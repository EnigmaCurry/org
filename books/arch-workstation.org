:PROPERTIES:

This book describes how I setup a Linux Workstation using Arch Linux,
installed remotely over SSH from a [[/arch-workstation/boomstick][BOOMSTICK]] live USB with its
=setup= command.

#+attr_shortcode: :style warning :title Work in progress
#+begin_notice
This book is unfinished and under active development. Chapters will
move, commands will change, and pages may contradict each other
while I am still working through them.

What is written takes a machine from an unplugged box to one that
boots on its own and accepts an SSH login -- the disk, the base
system, the bootloader, networking and accounts, all done by =setup=
-- and then keeps it in step with its host repo with =admin=, and adds
a sway desktop to it. The chapter on hardware-key =sudo= is not
written yet.

Be aware of what "tested" means here. BOOMSTICK's =just test-vm=
installs an *x86_64 PC* in a QEMU virtual machine with every prompt
answered, reboots it, logs in, and checks the result, including that
=admin diff= finds no drift and that pacman transactions are
snapshotted. =ENCRYPT=yes= does the same onto *LUKS*, answering the
passphrase prompt at boot. A *Raspberry Pi 5* has been installed on
real hardware, start to finish.

Not tested yet: =admin upgrade=, rolling back a snapshot, and logging
in to the desktop -- the test VM installs it and checks the login
screen, Nix and sway-home, but nobody has sat in front of it.
Hardware-key =sudo= is unwritten. Specific caveats are flagged in
place.

Read it as notes becoming a book rather than as a recipe that is
known to work start to finish.
#+end_notice

*** What is a workstation?

If a server is a machine whose role it is to serve applications to
many people over a network, a workstation is a machine whose role it
is to serve a local operator stationed at the computer.

A Linux workstation is therefore a personal computer that you use for
"work": development, administration, writing, research. Your
workstation might be a desktop computer, a laptop, or even a headless
box that you SSH into. It is the /role/ of the machine that matters,
not its form factor.

Your workstation may be connected to a broader network, but it is
primarily a client: a terminal, web browser, editor, and control
panel for other systems -- not a server for a wider audience. That
distinction is worth defending, for both security and data hygiene.
The two rules are simple: never keep production data on your work
machine, and never work directly in production.

Bend those rules however you like, but do so knowingly. A machine
that quietly becomes a /pet-with-ports/ costs you the ability to
reason clearly about where it is deployed, what it contains, and who
depends on it.

*** Why Arch Linux

Arch installs a base system and then stops. There is no distribution
layer sitting between you and the software you run: packages are
built close to upstream, defaults are upstream's defaults, and
nothing is configured on your behalf. The practical consequence is
that everything you read about a piece of Linux software applies to
your machine /literally/ rather than approximately -- including the
[[https://wiki.archlinux.org/][Arch Wiki]], which is the best operating system documentation anyone
is currently writing, and which assumes exactly the system you are
about to build.

It is a rolling release, so there are no version upgrades to schedule
and no six-month cliff where everything moves at once. =pacman= is
fast and legible, and =pacman -Qe= will tell you the complete list of
packages you explicitly asked for -- which turns out to be most of
what you need in order to rebuild a machine.

What Arch does /not/ give you is any guarantee that two machines
built from the same instructions are the same machine. The running
system is the source of truth, it drifts, and nothing but your own
discipline records how it got that way. That is the real trade, and
it is the one this book is organized around.

#+attr_shortcode: :style info :title The other side of the trade
#+begin_notice
The sibling [[/nixos-workstation][NixOS Workstation]] book takes the opposite position: the
configuration is the source of truth and the running system is built
from it, which buys reproducibility at the price of an indirection
layer between you and every upstream manual. Neither answer is wrong.
Pick the one whose failure mode you would rather live with.
#+end_notice

*** Declarative, or reproducible?

Those two words get used as though they meant the same thing. A
/declarative/ system is built from its configuration; a /reproducible/
one is one you can get back to. For servers and for dotfiles I want the
first, and NixOS with Home Manager is the best answer anyone has --
which is why the dotfiles in this book are still defined in Nix.

A workstation is where I part company, because declaring a machine
means knowing it first, and on hardware you have not met you do not:
the firmware is odd, the WiFi chip is a surprise, the kernel turns out
to be a vendor one. Arch lets you find that out on the machine and
write it down afterwards. On a new and unexplored box that makes it the
more reproducible of the two -- discovery comes first, and the host repo
records what you found.

None of that is a reason to stay. If you can spare the disk -- the Nix
store only grows, and every generation you keep grows it further --
NixOS is probably the better platform for a machine you mean to keep
for years: upgrades are atomic, a bad one rolls back, and the
configuration outlives the hardware it describes.

*** The install is a command, and a file

The official Arch install is a long sequence of commands typed into a
live system, and most of the ways it goes wrong come from typing them:
a value lost when an SSH session drops, a step run twice that should
have run once, a command typed into the chroot that belonged outside
it. This book does not ask you to type them. It uses =setup=, an
installer that ships on the BOOMSTICK and runs those commands for you,
in order, from a small description of the machine:

#+begin_run
setup host      # describe the machine
setup disk      # partition, format and mount it
setup install   # install, make it boot, network, accounts, SSH
setup reboot    # check everything, then reboot
#+end_run

and, for the rest of the machine's life, one more command:

#+begin_run
admin diff      # what changed on the machine that the repo does not say?
admin save      # write it into the repo, for you to review and commit
admin apply     # make the machine match the repo again
admin upgrade   # pacman -Syu, snapshotted, then apply
#+end_run

Be clear about what that trades away. =setup= is a long bash script
-- some fourteen hundred lines -- and it makes a great many choices
on your behalf, most of which you will never look at. In that sense
it /is/ a box you are asked to trust, and this book no longer walks
you through every command it runs. What it does instead is keep the
box open:

 - *It prints every command before it runs it*, so its output is a
   transcript of exactly what was done to the machine.
 - *Everything it leaves behind is plain text*: the host repo, and the
   aconfmgr configuration that describes the machine, are files you
   can read, diff and change.
 - *The pages that follow explain each stage* -- what it is for and
   why it is there -- rather than what to type.
 - *It is one file*, so when you do want to know exactly how
   something is done, =less $(which setup)= answers it.

That is less than a literate install, where you type every command
and understand each one as you go. It is more than an installer you
cannot read, and it does not mistype.

The description it works from is a small git repository, the *host
repo*: a file of answers (hostname, disk, encryption, time zone), a
package list, a list of services, and the handful of files that go
under =/etc=. It holds no secrets, and it ends up inside the installed
machine, where it is the record of how that machine was built -- and,
through =admin=, of every change made to it since.

#+attr_shortcode: :style warning :title What this does and does not buy you
#+begin_notice
Running =setup= again on another machine from the same host repo
reproduces the /steps/ and the /files/, not the /bytes/. Packages
will have moved on, and nothing here verifies that the result matches
a previous build. That is weaker than a pinned flake and considerably
stronger than memory.
#+end_notice

*** What you end up with

The core of this book builds a *minimal, headless base system*: a
partitioned and formatted disk, a bootloader, networking, your user
accounts, SSH and =sudo=. That base is deliberately the same work on
a desktop PC as on a Raspberry Pi, and it is a perfectly good
stopping point if what you wanted was a small server.

On top of that base it is kept *maintainable*: [[https://github.com/CyberShadow/aconfmgr][aconfmgr]] compares
the machine with its host repo in both directions, and snapper takes
a btrfs snapshot before and after every pacman transaction.

The graphical [[/arch-workstation/desktop][desktop]] comes after that, as its own optional chapter,
built on top of that base: sway from Arch, and the user's environment
from Nix and Home Manager.

*** Create your own custom installer

/This is your BOOMSTICK!/

Before any of that can happen, you need a way in. So the book starts
one step earlier than the install, by building the installer:
[[/arch-workstation/boomstick][BOOMSTICK]], an Arch live USB that joins your WiFi, brings up a
WireGuard tunnel to your own server, and lets you in over SSH with
your own keys. It is also where =setup= lives.

Write one and fill it in -- that is the [[/arch-workstation/boomstick][next chapter]] -- and the
target machine needs nothing but power and a USB port. No monitor, no
keyboard: you plug the stick in, power on, and get a root shell over
SSH from your own desk. Everything after that is =setup=.

*** Hardware this book covers

 - *x86_64 PCs*, booting *UEFI*. Legacy BIOS is not covered.
 - *Raspberry Pi 5*, which is the same work with a different
   bootloader and kernel. =setup= detects which one it is running on,
   and where the two differ, this book says so in place.

#+attr_shortcode: :style warning :title aarch64 means Arch Linux ARM
#+begin_notice
"Arch Linux" officially supports x86_64 only. On the Raspberry Pi the
distribution you are actually installing is [[https://archlinuxarm.org/][Arch Linux ARM]], a
separate community project that tracks Arch with its own mirrors and
its own package set, and the Pi 5 runs the Raspberry Pi Foundation's
kernel rather than a generic arm64 one. It is close enough that the
Arch Wiki remains useful, and far enough that some packages simply do
not exist there.

Linux on *Apple Silicon* should work on the same aarch64 footing, but
I have not tested it, and nothing in this book should be taken as a
claim that it does.
#+end_notice

*** Where this book sits among the others

 - [[/nixos-workstation][NixOS Workstation]] -- the same goal, built declaratively. If you want
   the machine described in code and rebuilt from that description,
   read that one instead.
 - [[/linux-workstation][Linux Workstation]] -- an older, archived book covering the same
   ground on Fedora Atomic. It is no longer maintained, but its
   [[/linux-workstation/sudo-2fa][Solokey]] hardware-key chapters carry over to any distribution.

*** This book is written with AI

I write this book with the help of AI, and I would rather say so
plainly than pretend otherwise. If that bothers you, that is fine --
I am not writing for that objection.

I do it because it makes the book a *malleable* product. The hard
part of documentation has never been producing prose; it is keeping
the prose true as the system underneath it changes. On a rolling
release that pressure is constant: commands, package names, and
defaults move under you. AI lets me revise the affected chapters
quickly and keep everything consistent, instead of letting pages
quietly rot. A book that is cheap to update is one that stays
correct.

What matters here is the *information* and the *flow*: that the steps
are accurate, that they are in the right order, and that the
reasoning behind them is clear. Hitting a particular literary tone or
vibe is not the point. I review what goes in, the decisions and the
setup described are genuinely mine and what I run, and the goal is
simply that you can follow it and end up with a working machine.

** Make the BOOMSTICK
:PROPERTIES:
:EXPORT_FILE_NAME: _index
:EXPORT_HUGO_SLUG: _index
:EXPORT_HUGO_WEIGHT: 250
:END:

Reinstalling Linux on a headless PC or a Raspberry Pi with the
official installer is a tedious affair. Before the target machine
will accept a remote login, there is a handful of chores to be done
by hand, every single time: write the ISO to a stick, borrow a
monitor and keyboard, type a WiFi passphrase into =iwctl=, set a root
password or paste in an authorized key, get onto the same network as
the target, and clear the machine's stale entry out of
=known_hosts=.

[[https://github.com/EnigmaCurry/boomstick][BOOMSTICK]] does all of those chores for you, once, at your desk. You
write the image to a USB stick, drop your WiFi, WireGuard and SSH
settings onto it, and from then on you plug it in, power on, and SSH
in from wherever you are. This chapter builds it; every chapter after
it assumes you booted the target machine from one.

*** What's on the stick

BOOMSTICK is the stock Arch Linux installer -- archiso's =releng=
profile -- with a few additions layered on top:

 - *WiFi*, optionally: iwd joins your networks automatically, with
   wired ethernet preferred when both are available.
 - *WireGuard*, optionally: =wg-quick@wg0= brings up a tunnel to your
   own server at boot, retrying until the endpoint's DNS name
   resolves, so the stick has the same address on any network.
 - *SSH*: sshd lets you in as root with your =authorized_keys=, which
   is the one thing you must supply. Password login is never
   permitted.
 - *A stable identity*: the hostname is always =boomstick=, and the
   stick generates its SSH host keys on first boot and keeps them.
 - *=setup=*, the installer the rest of this book uses.
 - *A boot webhook*, optionally, which notifies you (via [[https://ntfy.sh][ntfy]], for
   example) with the stick's LAN, public and WireGuard addresses once
   it is up.

One image boots both x86_64 PCs (UEFI only) and the Raspberry Pi 5,
so a single stick in your bag covers every machine in this book.

*** The image is generic; the stick is yours

The image itself contains no secrets, so you can build it once, and
so can anyone else. Your WiFi passwords, WireGuard key, SSH keys and
webhook URL go into a =boomstick/= directory on the stick's
FAT32 partition, which you fill in /after/ writing the image. That
partition is readable from any computer, so you edit those files with
whatever editor you like, and the live system reads them again on
every boot.

#+attr_shortcode: :style warning :title A configured stick is a key
#+begin_notice
The secrets on the stick are stored in plain text, readable by any
computer it is plugged into. Anyone holding it can join your WiFi and
your VPN. Keep it in your possession, and give each stick its own
WireGuard key so that you can revoke a lost one without touching the
others.
#+end_notice

The rest of this chapter goes through it in order, beginning with
[[/arch-workstation/boomstick/build][Build the image]].

** Build the image
:PROPERTIES:
:EXPORT_FILE_NAME: build
:EXPORT_HUGO_SLUG: build
:END:

Everything on this page runs on your own workstation.

You do not need archiso, or any Arch packages at all: the build runs
inside an =archlinux= container, so the host's own distribution does
not matter. You need rootless [[https://podman.io/][Podman]], [[https://github.com/casey/just][just]], about 8 GB of free disk
space, and an internet connection.

Because the image holds both an x86_64 and an ARM system, whichever
half does not match your own machine is built under qemu-user
emulation, so you also need the static qemu-user emulators registered
with binfmt_misc. On Arch Linux, that is all of:

#+begin_run
sudo pacman -S --needed podman just git qemu-user-static qemu-user-static-binfmt
#+end_run

On Debian, Ubuntu or Fedora, the emulator package is called
=qemu-user-static=.

#+attr_shortcode: :style info :title Building on macOS
#+begin_notice
Because the work happens inside a container, a Mac builds the image
too -- this is tested, not theoretical. Install the tools and start a
Podman VM with enough memory to do the build:

#+begin_src bash
brew install podman just
podman machine init --cpus 4 --memory 3072
podman machine start
#+end_src

On Apple Silicon the two halves swap roles: the Raspberry Pi image
builds natively and the x86_64 one runs under emulation, which is the
reverse of what happens on a Linux PC. The rest of this page is
unchanged, except for writing the image to the stick.
#+end_notice

*** Build

#+begin_run
git clone https://github.com/EnigmaCurry/boomstick.git
cd boomstick
just build-usb
#+end_run

The build takes no input, because there is nothing to configure yet:
the result is the same for everybody. The first run pulls the
=archlinux= container image and downloads about 1 GB of packages;
later builds reuse a package cache and finish in a few minutes. You
end up with =out/boomstick-usb-<date>-x86_64+rpi5.img=, about 2.7 GB.

#+attr_shortcode: :style tip
#+begin_notice
If you only ever install one kind of machine, =just build= (x86_64
only) and =just build-rpi5= (Raspberry Pi 5 only) produce smaller
images that need no emulation on a matching host.
#+end_notice

*** Write it to a USB stick

Find your stick with =lsblk=, then write the image to it. Double
check the device name, because this erases the whole stick:

#+begin_run
sudo dd if=out/boomstick-usb-<date>-x86_64+rpi5.img \
  of=/dev/sdX bs=4M status=progress oflag=sync
#+end_run

On macOS the device names and flags differ: find the disk with
=diskutil list=, then unmount and write it to the /raw/ device, which
is much faster than the buffered one:

#+begin_src bash
diskutil unmountDisk /dev/diskN
sudo dd if=out/boomstick-usb-<date>-x86_64+rpi5.img of=/dev/rdiskN bs=4m
#+end_src

Everything that makes the stick yours is configuration, and changing
that later never requires another build -- so this is the only time
you have to think about the image at all for a good while. (It is not
quite "once, ever": see [[/arch-workstation/boomstick/provision][Changing it later]] for the handful of
things that are frozen into an image.) Configuration starts on the
next page,
[[/arch-workstation/boomstick/secrets][SSH keys, WiFi and the webhook]].

** SSH keys, WiFi and the webhook
:PROPERTIES:
:EXPORT_FILE_NAME: secrets
:EXPORT_HUGO_SLUG: secrets
:END:

You can edit the configuration directly on the stick, but it is
easier to keep it in the repo, next to the build, and copy it over.
Running =just config= creates a =secrets/= directory -- git-ignored,
and readable only by you -- full of commented-out templates:

#+begin_run
just config
#+end_run

#+begin_stdout
created: secrets/ssh/authorized_keys  (edit it)
created: secrets/webhook.env  (edit it)
created: secrets/wifi/EXAMPLE.psk.example  (edit it)
created: secrets/wireguard/wg0.conf  (edit it)
#+end_stdout

Of those four files, *only =secrets/ssh/authorized_keys= is
required*. The others are opt-in: leave any of them commented out and
the stick simply boots without that feature.

*** SSH keys (required)

The only other file you *must* fill in is
=secrets/ssh/authorized_keys=: put the public key or keys you will
log in with, one per line, exactly as in any other =authorized_keys=
file. Without at least one key, nobody can log in over SSH at all,
because the stick never allows password logins.

If your keys are on GitHub, you can fetch them straight from your
profile, since GitHub publishes every user's public keys:

#+begin_run
curl -fsSL https://github.com/YOUR_USERNAME.keys >> secrets/ssh/authorized_keys
#+end_run

Read the file afterwards to make sure you got the keys you expected,
and remove any you do not want to have root on the stick.

*** WiFi (optional)

WiFi is optional; without it, the stick is wired-only. Add one file
per network to =secrets/wifi/=, in iwd's own format, named after the
SSID:

#+attr_shortcode: :file secrets/wifi/My Network.psk
#+begin_edit
[Security]
Passphrase=your wifi password
#+end_edit

You can add as many networks as you like, and iwd joins whichever one
is in range. An SSID with characters other than letters, digits,
spaces, =-= and =_= needs a hex-encoded filename; the
=EXAMPLE.psk.example= template explains how.

*** The boot webhook (optional)

To get a notification when the stick boots, set a URL in
=secrets/webhook.env=:

#+attr_shortcode: :file secrets/webhook.env
#+begin_edit
WEBHOOK_URL=https://ntfy.sh/a-long-random-topic
#+end_edit

Once the network is up and WireGuard connects -- or gives up after
two minutes -- the stick POSTs a plain-text message there, which
works with [[https://ntfy.sh][ntfy]] or a [[https://github.com/matrix-org/matrix-hookshot][matrix-hookshot]] generic webhook.

#+attr_shortcode: :style warning
#+begin_notice
The message includes your IP addresses, and anyone who knows an
ntfy.sh topic name can read it. Pick a long random topic, or use a
server with access control.
#+end_notice

With those in place, the stick is already usable on a network you
control. The next page adds [[/arch-workstation/boomstick/wireguard][WireGuard]], which is what makes it
usable on one you do not.

** Configure WireGuard
:PROPERTIES:
:EXPORT_FILE_NAME: wireguard
:EXPORT_HUGO_SLUG: wireguard
:END:

WireGuard is optional. Without it, the stick still boots, joins your
WiFi and accepts your SSH keys -- it is simply reachable only on
whatever LAN it lands on, at whatever address DHCP gave it. That is
perfectly workable when the target machine is sitting on your own
network.

What the tunnel buys you is a *fixed* address that does not depend on
which network the machine is plugged into. The stick answers at the
same WireGuard address on every network and in every machine, so you
can =ssh boomstick= without discovering anything first, and you can
install a machine that is nowhere near you.

#+attr_shortcode: :style info :title Skipping it
#+begin_notice
To leave WireGuard out, just leave =secrets/wireguard/wg0.conf= as
the template generated it. =just provision= prints a warning that
there is no WireGuard and carries on.

If you /do/ fill it in, it has to be complete: provision refuses a
=wg0.conf= with no =PrivateKey=, or one with no
=PersistentKeepalive=, rather than handing you a stick that cannot
phone home.
#+end_notice

*** Give the stick its own peer

The stick is a WireGuard client -- a /spoke/ -- of a server you
already run. Most VPN servers and routers will provision a client for
you: you add a new peer on the server, and it hands you a ready-made
config with the client's private key, its address, and the server's
public key and endpoint.

#+attr_shortcode: :style info :title If you do not have a server yet
#+begin_notice
Standing up the hub is out of scope for this book, and will
eventually get a book of its own. In the meantime, my
[[https://github.com/EnigmaCurry/nixos-vm-template][nixos-vm-template]] has a =wireguard= profile that does it:
=just wireguard <hub>= mints the hub and a config for every peer, and
[[https://github.com/EnigmaCurry/nixos-vm-template/blob/master/WIREGUARD.md][WIREGUARD.md]] walks through the whole thing.

Add the stick there as an ordinary spoke, and treat it as the
wizard's "generic Linux client" case. The =.conf= it generates
already carries the =AllowedIPs= and =PersistentKeepalive = 25= lines
the stick requires; the only difference is that it goes into
=secrets/wireguard/wg0.conf= here, instead of straight into
=/etc/wireguard/wg0.conf= on a running machine.
#+end_notice

Give the stick a peer of its own -- do not reuse your laptop's -- and
paste that config in:

#+attr_shortcode: :file secrets/wireguard/wg0.conf
#+begin_edit
[Interface]
PrivateKey = <the stick's private key>
Address = 10.0.0.2/32

[Peer]
PublicKey = <your server's public key>
Endpoint = vpn.example.com:51820
AllowedIPs = 10.0.0.0/24
PersistentKeepalive = 25
#+end_edit

If your server does not provision clients for you, =just keygen=
makes a fresh key pair for the stick. Put the private key in
=wg0.conf=, and add the public key to your server as a new peer, with
=AllowedIPs= set to the stick's address (=10.0.0.2/32= here).

*** Why the keepalive matters

Check that the config has a =PersistentKeepalive= line, and add one
if your server left it out. The stick is the one behind NAT, usually
on some network you do not control, so it has to keep the tunnel open
itself. Without the keepalive, the server cannot reach the stick
until the stick happens to send it something -- and you cannot SSH
in.

The =Endpoint= may be a DNS name: the tunnel keeps retrying until it
resolves, which helps when the stick boots before the network is
fully up. If you want to resolve names through the VPN, a =DNS= line
works too.

With the configuration written, [[/arch-workstation/boomstick/provision][Provision the stick]] copies it onto
the stick itself.

** Provision the stick
:PROPERTIES:
:EXPORT_FILE_NAME: provision
:EXPORT_HUGO_SLUG: provision
:END:

With the files filled in, plug in the stick you wrote earlier and
copy them onto it:

#+begin_run
just provision
#+end_run

=just provision= finds the stick by its =BOOMSTICK= partition
label, mounts it if it has to, writes =boomstick/=, and unmounts
it again so it is ready to pull.

Before copying anything, it checks the files for the mistakes that
would leave a headless machine unreachable, and fails here, at your
desk, instead of later on the other side of the room. An
=authorized_keys= with no keys in it is refused outright, since
nobody could log in. A =wg0.conf= that is filled in but missing its
=PrivateKey= or =PersistentKeepalive= is refused too. A =wg0.conf=
left untouched is fine -- that is just a stick without WireGuard, and
it says so.

*** Editing the stick by hand instead

If you would rather skip =secrets/= and edit the stick directly,
mount its partition with =udisksctl= rather than =sudo mount=:

#+begin_run
udisksctl mount -b /dev/sdX1
#+end_run

FAT stores no file ownership, so a plain =sudo mount= makes every
file look like it belongs to root, and you cannot edit them as
yourself. =udisksctl= mounts it as your own user, at
=/run/media/$USER/BOOMSTICK=.

*** Changing it later

Everything that makes the stick yours lives in a handful of plain
files. When you move to a new WiFi network, rotate a WireGuard key,
or add someone's SSH key, you edit a file on the stick -- or in
=secrets/=, then run =just provision= again -- and you are done, with
nothing to rebuild.

=boomstick-config= re-reads all of it on /every/ boot, which is what
makes that true. The same mechanism updates =setup= itself: =just
provision= copies the current installer to =boomstick/bin/setup=, and
the live system installs that copy over its own at boot. So a fix to
=setup= reaches a stick without a rebuild.

What a stick /cannot/ grow into is anything that lives in the live
system itself -- the squashfs the image was built from:

 - the *package set*: the live system's own =git=, =cryptsetup=,
   =archlinuxarm-keyring= and the rest,
 - the *kernel and initramfs*, and
 - =boomstick-config=, =boomstick-webhook= and =boomstick-motd=, the
   boot-time logic itself.

Those are frozen at build time, and the way to move them forward is to
build a new image and write it to the stick again -- then =just
provision= to put your configuration back, since a fresh image carries
only the templates.

#+attr_shortcode: :style warning :title Installing packages on the live system does not stick
#+begin_notice
The live system boots =copytoram=auto=, and its root is a tmpfs
overlay. =pacman -Sy something= works and is a perfectly good way out
of a hole, but the next boot has forgotten it. Treat it as a patch for
the session, not a repair to the stick.

The corollary is worth knowing before you keep an old stick around: a
stick whose image predates a feature in that frozen half cannot be
provisioned into having it. =bin/setup= is only picked up because
=boomstick-config= looks for it, so a stick older than /that/ cannot
be given a newer =setup= either, however many times you provision it.
Rebuild instead.
#+end_notice

*** Updating from the stick itself

=just provision= needs your workstation and a checkout of the
repository. =boomstick-update=, on the live system, does the same job
over the network when you have neither -- which, for a tool meant for
installing machines in other rooms and other buildings, is a situation
that comes up.

#+attr_shortcode: :style secondary :title Run this on the live system:
#+begin_run
boomstick-update
#+end_run

It clones the repository, says where from and which commit it resolved
to, shows a *diff* of every helper that would change, and asks. Enter
declines. What you accept is written to =boomstick/bin/= on the stick,
so the next boot has it, /and/ to =/usr/local/bin= in the running
system, so this boot has it too -- no reboot in between. Each run
appends a line to =boomstick/UPDATES.txt=, so the stick carries a
record of what it has been given.

It updates BOOMSTICK, not Arch. The live system stays the one the image
was built with -- the same =pacman=, the same keyring, the same
kernel -- so this is no answer to an image going stale on a rolling
release. Its reach is exactly =just provision='s: the helpers, and
nothing else. =boomstick-config= is deliberately left out too, since it
is what installs the others at boot and a broken copy would take
configuration down with it on every later boot. For the package set,
the kernel, or that, rebuild.

It refuses to run while something is mounted at =/mnt=, since replacing
=setup= under a running install is nobody's idea of a good afternoon,
and when the stick is not plugged in -- =copytoram= means the live
system keeps going without it, but then there is nothing to write to.

=--ref= takes a branch or a tag, and defaults to the repository's
default branch, which is not necessarily where your stick came from. A
stick built from a topic branch will find the default branch has none
of its helpers, and =boomstick-update= says so rather than reporting
everything up to date.

#+attr_shortcode: :style warning :title It verifies nothing
#+begin_notice
The commits are not signed, so the SHA it prints is a record of what
was pulled, not proof of who wrote it -- and this installs a program
that runs as root on a machine about to repartition a disk. The diff is
the safeguard, which is why it is not optional. Read it.
#+end_notice

*** Upgrading a stick you already have

Writing a new image to a stick erases the only copy of some of its
secrets. The WireGuard key and the SSH host keys it made on its first
boot exist nowhere else: =secrets/= on your workstation may be long
gone, or may never have been on /this/ workstation at all. So take them
off the stick /before/ you write anything to it.

#+attr_shortcode: :style secondary :title Run this on your workstation:
#+begin_run
git clone https://github.com/EnigmaCurry/boomstick
cd boomstick
just adopt
#+end_run

=just adopt= finds the stick by its =BOOMSTICK= label and copies back
what the repository cannot regenerate -- the WiFi PSKs, =wg0.conf=,
=authorized_keys=, =webhook.env= and =ssh/host/= -- into =secrets/=,
owned by you and readable by nobody else. =README.txt= and =bin/= are
left alone: those come from the repository, not from the stick.

It refuses to overwrite a =secrets/= that already has files in it, and
says which ones clashed, so aiming it at the wrong stick cannot quietly
replace a working configuration with somebody else's. =just adopt
--force= when the stick really is the one to keep.

With the secrets safe, the rest is the ordinary path: [[/arch-workstation/boomstick/build][build]] a new
image, write it to the stick, and =just provision= to put the
configuration back.

#+attr_shortcode: :style info :title The stick keeps its identity
#+begin_notice
Adopting =ssh/host/= is what carries the stick's SSH host keys across
the rewrite, so =ssh boomstick= does not start warning about a changed
host key afterwards. If you would rather it got new ones, delete
=secrets/ssh/host/= before provisioning and it will generate a fresh
set on its next first boot.
#+end_notice

** How it works under the hood
:PROPERTIES:
:EXPORT_FILE_NAME: internals
:EXPORT_HUGO_SLUG: internals
:END:

There is very little magic involved. Early in boot -- before iwd,
WireGuard, sshd or the webhook start -- a small service called
=boomstick-config= finds the config partition and copies
=boomstick/= into the live system, which runs entirely in RAM.
Each file lands where the stock tools expect it, readable only by
root:

| On the stick          | In the live system           |
|-----------------------+------------------------------|
| =wifi/*.psk=          | =/var/lib/iwd/=              |
| =wireguard/wg0.conf=  | =/etc/wireguard/wg0.conf=    |
| =ssh/authorized_keys= | =/root/.ssh/authorized_keys= |
| =webhook.env=         | =/etc/boomstick/webhook.env= |
| =ssh/host/*=          | =/etc/ssh/=                  |
| =bin/setup=           | =/usr/local/bin/setup=       |

Nothing else is ever written back to the stick. The one exception is
the SSH host keys on the first boot: the partition is remounted
read-write just long enough to save them, then read-only again. That
is what keeps the fingerprint stable from one boot to the next.

*** Why the partition label matters

The service finds the partition by its =BOOMSTICK= label, and that
label matters more than it looks. The Arch live system boots with
=copytoram=: on a machine with enough memory, it copies itself into
RAM and lets go of the boot partition before any of this runs. So the
service cannot simply look at "the partition I booted from"; it
searches for a filesystem labelled =BOOMSTICK=, mounts it, and
unmounts it again.

If you relabel the partition, the stick still boots -- but
unconfigured.

A nice side effect is that the configuration does not have to be on
the stick you booted from. Any FAT32 USB stick labelled =BOOMSTICK=
with a =boomstick/= directory on it works too; start from a
copy of the repo's =config-templates/=. Just do not plug in two of
them at once, because the first one found wins.

And a stick with no configuration at all still boots. It simply has
no WiFi, no VPN, no SSH login and no webhook, and says so on the
console.

*** One stick, two architectures

The combined image boots an x86_64 PC and a Raspberry Pi 5 from the
same partition, which sounds like it ought to need something clever.
It does not. There is one MBR disk image with a single FAT32
partition on it, and the whole trick is that the two firmwares never
look at the same files:

#+begin_src text
config.txt cmdline.txt kernel8.img initramfs-linux.img *.dtb overlays/   # Pi 5 firmware
EFI/BOOT/BOOTx64.EFI  loader/  arch/boot/x86_64/                         # x86_64 UEFI (systemd-boot)
arch/x86_64/airootfs.sfs   arch/aarch64/airootfs.sfs                     # the two live systems
boomstick/                                                               # your configuration
boot/<uuid>.uuid                                                         # how each initramfs finds the stick
#+end_src

The Pi's firmware reads only the top-level files. There is no boot
loader on the Pi at all: the firmware itself loads =kernel8.img=, the
initramfs and the device trees straight off the FAT partition, and
takes its kernel command line from =cmdline.txt=. UEFI firmware, for
its part, looks only in =EFI/= and =loader/=, where it finds
systemd-boot. Neither one has any idea the other's files are sitting
next to it.

Once a kernel is running, its initramfs mounts
=arch/<its own architecture>/airootfs.sfs=. That is why there are two
=airootfs.sfs= files: they are two complete live systems, one per
architecture, and each boot only ever touches one of them.

*** How each half finds the stick

archiso normally identifies the medium it booted from by the ISO's
volume UUID -- which a FAT32 stick does not have, because there is no
ISO filesystem involved. So it falls back to a second method: it
searches the attached disks for a file at =boot/<uuid>.uuid= and uses
whichever one matches the UUID it was told to expect. The Pi gets
told through =cmdline.txt=:

#+begin_src text
archisobasedir=arch archisosearchuuid=1234-5678 console=serial0,115200 console=tty1
#+end_src

This is the same mechanism archiso provides for copying an ISO onto a
FAT32 stick, used here for both halves.

It is worth noticing that this is a /different/ search from the one
that finds =boomstick/=. The live system looks for its
configuration by the =BOOMSTICK= filesystem label, as described
above, because by then it may have let go of the boot device
entirely. The two lookups are independent, which is exactly why the
configuration can live on a second stick.

*** How the combined image is built

=just build-usb= builds an x86_64 ISO first, then builds the Pi image
and merges the ISO's UEFI boot files and live system into the Pi
image's FAT32 partition. The ISO is only an intermediate -- it is
where systemd-boot and the x86_64 kernel come from -- and it is
deleted once the combined image exists.

#+attr_shortcode: :style warning :title What the combined image costs
#+begin_notice
 - *x86_64 is UEFI only*, and Secure Boot must be off.
 - The partition is FAT32 with MBR type =0x0c=, because that is what
   the Pi requires. UEFI firmware is /supposed/ to boot from an EFI
   System Partition (type =0xef=), and although nearly all of it will
   also boot a FAT32 USB stick carrying =EFI/BOOT/BOOTx64.EFI=, a
   strict implementation is entitled not to.
 - Both halves read the same =boomstick/=, so a PC and a Pi
   booted from this stick present the *same* SSH host key and claim
   the *same* WireGuard address. That is a feature when you use them
   one at a time, and a problem if you boot two at once -- they will
   fight over the peer address. Install one machine at a time, or
   give the second stick its own key.
#+end_notice

This chapter takes you from a machine with no operating system on it
to a root shell on that machine, reached over SSH from the computer
you are already sitting at. Nothing is written to the target's disk
here. The live system runs entirely in RAM, so everything in this
chapter is reversible by pulling the power.

What you need before starting:

 - A [[/arch-workstation/boomstick][BOOMSTICK]], written and filled in as in the previous chapter.
   It carries =setup=, which the rest of the book uses.
 - The target machine, with power and a network connection.
 - Your own workstation, with an SSH client.

*** Plug in and power on

Plug the stick into the target machine. Connect ethernet if you have
it -- wired is preferred automatically when both are available --
otherwise make sure the machine is in range of one of the WiFi
networks you put on the stick. Then power it on.

You do not need a monitor or a keyboard. There is no boot menu to
answer and no prompt to type into.

*** Getting the machine to boot from USB

The one thing that may need a monitor, exactly once, is convincing
the machine's firmware to boot the stick at all.

On an *x86_64 PC*, most firmware offers a one-time boot device menu,
usually behind =F12=, =F11=, =F8= or =ESC= during power-on -- the key
varies by manufacturer. Pick the USB device from that menu, or enter
the firmware setup and move USB ahead of the internal disk in the
boot order permanently. Set it permanently if you expect to reinstall
this machine again.

#+attr_shortcode: :style warning :title UEFI only
#+begin_notice
This book installs UEFI systems. If the machine's firmware is set to
legacy BIOS or "CSM" mode, switch it to UEFI before going any
further, because =setup= installs systemd-boot onto an EFI System
Partition. =setup disk= checks which mode you actually booted in,
and refuses to touch the disk if it was legacy BIOS.
#+end_notice

On a *Raspberry Pi 5* there is no boot menu, and the factory boot
order works against you. The default is =BOOT_ORDER=0xf461=, which
tries the SD card, then NVMe, then USB -- so a Pi with a bootable
NVMe drive never reaches the stick at all.

Remove any SD card before powering on. If the machine also has an
NVMe drive you cannot simply unplug, change the boot order once, from
whatever system you can currently boot on that Pi:

#+attr_shortcode: :style secondary :title Run this on the Raspberry Pi:
#+begin_run
rpi-eeprom-config --edit     # set BOOT_ORDER=0xf641, then reboot
#+end_run

Those numbers are easier to read once you know the trick: each hex
digit names one boot device, and the Pi works through them *right to
left*. =1= is the SD card, =4= is USB, =6= is NVMe, and the leading
=f= means "start the list over again".

So the factory =0xf461= is SD → NVMe → USB, and =0xf641= is SD → USB
→ NVMe: the same three devices, with USB promoted above NVMe.

The setting lives in the Pi's EEPROM, so you only do this once. With
the stick removed, the Pi goes back to booting its NVMe as usual.

*** Wait for the notification

If you set a webhook URL on the stick, the live system posts to it
once the network is up and WireGuard has either connected or given up:

#+begin_stdout
boomstick is up (boomstick 2026.10.24)
LAN: 192.168.1.50/24 on enp1s0
Public: 203.0.113.4
WireGuard: 10.0.0.2/32 on wg0 (handshake 3s ago)
#+end_stdout

That message is how you learn the machine is ready and where it
landed. If WireGuard failed, the last line says why instead, which is
considerably more useful than silence.

Without a webhook, you already know where to find it: the stick's
WireGuard address is fixed, set by you when you provisioned it, and
it is the same on every machine you plug the stick into. Give it
thirty seconds or so after power-on and try to connect.

#+attr_shortcode: :style tip
#+begin_notice
If the network did not come up and you are working at the console
instead, everything from the next chapter onward is identical: log in
as root and run =setup= there. Only the [[/arch-workstation/boot/ssh][Connect over SSH]] page is
specific to the headless path.

=setup= is a single script, so the official [[https://archlinux.org/download/][Arch Linux ISO]] can run it
too, once you copy it across. That path is not tested.
#+end_notice

** Connect over SSH
:PROPERTIES:
:EXPORT_FILE_NAME: ssh
:EXPORT_HUGO_SLUG: ssh
:END:

Every command on this page runs on *your own workstation*, not on the
target.

*** Name the stick in your SSH config

The live system presents the same hostname, the same WireGuard
address and the same SSH host key no matter which machine it is
plugged into, so it behaves like one fixed host on your network. That
makes it worth a permanent entry in your SSH config, rather than
typing an address each time:

#+attr_shortcode: :file ~/.ssh/config
#+begin_edit
Host boomstick
    HostName 10.0.0.2
    User root
    HostKeyAlias boomstick
#+end_edit

Replace =10.0.0.2= with whatever address you gave the stick in its
WireGuard config.

=HostKeyAlias= is the part that earns its keep. It files the host key
in =known_hosts= under the name =boomstick= instead of under an IP
address, so you accept the fingerprint once, ever, and never have to
clean up =known_hosts= after an install again.

*** Log in

#+begin_run
ssh boomstick
#+end_run

If the tunnel is not up, or you are not using WireGuard at all, use
the LAN address from the webhook notification instead. Overriding
only the address keeps the host entry's name, so SSH still checks the
same key:

#+begin_run
ssh -o HostName=192.168.1.50 boomstick
#+end_run

You are logged in as =root=. Password authentication is disabled on
the stick, so if you are refused, the problem is your
=authorized_keys= file on the config partition rather than anything
on the target machine.

*** About that host key

On its first boot the stick generates its SSH host keys and saves
them back to its own config partition, so the fingerprint stays the
same from then on. If you want to check it against the stick before
trusting it, compute it from the config partition with the stick
plugged into your workstation:

#+begin_run
ssh-keygen -lf /run/media/$USER/BOOMSTICK/boomstick/ssh/host/ssh_host_ed25519_key.pub
#+end_run

#+attr_shortcode: :style warning :title The fingerprint identifies the stick, not the machine
#+begin_notice
Because the host key lives on the USB stick, every machine you
install with it presents the *same* key. A matching fingerprint tells
you "this is my stick", not "this is the particular computer I think
I am talking to". That is a fine trade for an installer you carry in
your pocket, but do not carry the habit over to the installed
system -- the machine you build in this book generates its own host
key, unique to it.
#+end_notice

#+attr_shortcode: :style warning :title Tested on x86_64 only
#+begin_notice
=setup= is on the =setup= branch of [[https://github.com/EnigmaCurry/boomstick][BOOMSTICK]]. Its =just test-vm=

You have a root shell on the live system. Four commands install the

| Command           | What it does                                                 | Changes the target? |
|-------------------+--------------------------------------------------------------+---------------------|
| [[/arch-workstation/setup/host][setup host]]        | Asks what this machine is, and writes it down                | No                  |

| [[/arch-workstation/setup/check][setup reboot]]      | Checks everything, then unmounts and reboots                 | No                  |

Run =setup= with no arguments and it shows the same list, with a mark
next to each step already done, and offers to run the next one.

*** How setup behaves

 - *It reads the host repo and nothing else.* Every step starts by
   reading =/root/arch/host.env=, never a shell variable, so a dropped
   SSH session loses nothing: reconnect and run the step again.
 - *Every step is safe to run again.* A step that has already been
   done says so and skips, or only does what is missing. The one step
   that cannot be repeated -- erasing the disk -- makes you type the
   hostname first.
 - *It shows you before it does anything.* Each step prints a review
   screen and asks. =setup --yes <step>= answers yes for you, except
   to erasing a disk.
 - *It walks you through.* =setup= with no arguments shows which steps
   are done and offers to run the next one, then the one after that,
   so an install is one command and a series of questions rather than
   four commands typed from the book. Declining stops there, and so
   does a step that fails. The reboot at the end is the exception:
   pressing Enter /declines/ it, because wanting a look around before
   the machine goes down is the normal case.
 - *It prints what it runs.* Every command is echoed with a leading
   =+= before it runs, so the output is a transcript of exactly what
   was done to the machine.
 - *It keeps that transcript.* All of it is written to
   =logs/000_SETUP.txt= in the host repo, committed, and copied to the
   installed machine, with a header per step recording the time,
   whether the clock was synchronised, and which image did the
   installing. Months later, =git log= in =~/arch= still answers "how
   was this machine built?". Passwords and passphrases are not in it:
   they are read from the terminal, never printed.
 - *It is one readable file.* =setup= is a bash script at
   =/usr/local/bin/setup=. =less $(which setup)= is the documentation
   of last resort, and the pages that follow say which part of it does
   what.

=just provision= copies the current =setup= onto the stick's config
partition, and the live system prefers that copy to the one built
into the image, so a fix to =setup= reaches a stick without
rebuilding it.

*** Three machines

Three machines are in play during an install, and the command blocks
in this chapter say which one each runs on:

| Machine          | What it is                                                                |
|------------------+---------------------------------------------------------------------------|
| your workstation | The computer you are already sitting at, running your editor and SSH client. |
| the live system  | The target machine booted from the BOOMSTICK, running in RAM. =setup= runs here. |
| the target       | The system being installed, mounted under =/mnt= until it boots on its own. |

=setup= works on the target from the live system, using =arch-chroot
/mnt= for each command that has to run inside it, so you never have to
keep track of which side of the chroot you are on.

** Describe the machine
:PROPERTIES:
:EXPORT_FILE_NAME: host
:EXPORT_HUGO_SLUG: host
:END:

The first step changes nothing on the target. It asks a few
questions and writes the answers into the *host repo*, which every
later step reads.

#+attr_shortcode: :style secondary :title Run this on the live system:
#+begin_run
setup host
#+end_run

*** Answer the prompts

Each prompt is pre-filled with its default, which you can edit in
place or accept with Enter.

#+begin_annotate
#+begin_src bash
== Describe this machine ==
Machine: x86_64 PC, UEFI
? Hostname: archlinux
#+end_src

The name you will type into =ssh= for the rest of the machine's
life, so something short and memorable beats something descriptive.
=setup= writes it straight into the target's =/etc/hostname= rather
than using =hostnamectl=, which inside a chroot talks to the /live
system's/ systemd and would rename the stick instead.
#+end_annotate

#+begin_annotate
#+begin_src bash
? Install to which disk?
  1) /dev/disk/by-id/nvme-XP1000F256G_2213E5A1B2C3       238.5G  nvme  XP1000F256G  (nvme0n1)
  2) /dev/disk/by-id/ata-Samsung_SSD_870_S5Y1NG0R        931.5G  sata  Samsung SSD 870  (sda)
  (/dev/sdb, the BOOMSTICK you booted from, is not offered)
? Number (1): 
#+end_src

The disk is recorded by its =/dev/disk/by-id/= name, which belongs to
that physical drive, rather than =/dev/nvme0n1=, which belongs to
whatever order the kernel found the drives in this time. The stick you
booted from is never offered: =setup= finds it by its =BOOMSTICK=
partition label and leaves it off the list, and refuses it later even
if you write it into the host file by hand.
#+end_annotate

#+begin_annotate
#+begin_src bash
? Encrypt the root filesystem with LUKS? (yes/no): no
#+end_src

Full-disk encryption protects the data on a machine that is stolen,
resold, or returned under warranty. It does nothing for a machine
that is already running and unlocked: the threat it addresses is
physical possession of the disk.

The cost is a passphrase at every boot, which is a real cost on a
headless machine in another room. A laptop is an obvious yes; a home
server that must come back up unattended after a power cut is an
obvious no.

On a Raspberry Pi, =setup= warns before asking. The Pi has no
bootloader that can prompt for a passphrase, so the prompt comes from
the initramfs on the console and serial line -- of no use on a Pi
with neither attached. Unlocking a headless Pi over the network needs
an initramfs with networking and SSH, which this book does not set
up. If the Pi is headless, leave encryption off.
#+end_annotate

#+begin_annotate
#+begin_src bash
? Swap file size, or 0 for none: 8g
#+end_src

Swap is worth having even with plenty of memory: it gives the kernel
somewhere to put pages that genuinely are not being used, freeing real
memory for the page cache, and it turns "the machine froze solid" into
"the machine got slow" when something runs away with allocations.
Matching your RAM is only strictly necessary for hibernation, which
this book does not set up.
#+end_annotate

#+begin_annotate
#+begin_src bash
? Time zone: America/Denver
? Locale: en_US.UTF-8
? Console keymap: us
#+end_src

The time zone defaults to the live system's (UTC unless you changed
it); =ls /usr/share/zoneinfo= lists them. The locale is checked
against =/etc/locale.gen=. Pick a UTF-8 one: a non-UTF-8 default is
why box-drawing characters in programs like =lsblk= degrade into =|-=,
and it causes stranger problems than that in anything handling text.
The keymap is for the text console only, which on a machine you reach
over SSH you may never see -- until a rescue prompt.
#+end_annotate

#+begin_annotate
#+begin_src bash
? Passwordless sudo for admin? (yes/no): yes
? Extra packages to install (blank for none): just tmux
#+end_src

=setup= always creates two accounts:

| Account | UID  | Groups           | What it is for                          |
|---------+------+------------------+-----------------------------------------|
| =admin= | 1000 | =admin=, =wheel= | Administration, and SSH login           |
| =user=  | 1001 | =user=           | Everything else. No special privileges. |

The split is the point. Day-to-day work -- editing, browsing,
building, running other people's code -- happens as =user=, an
account that cannot reconfigure the system even by accident. When
you intend to administer the machine, you log in as =admin=.

Whether =admin= needs a password for =sudo= is the question. Saying
yes means anything that gets a shell as =admin= has root, which is a
real reduction in depth. The reasoning for it here: SSH is key-only,
root cannot log in, and a sudo password mostly protects against
someone who already has an =admin= shell -- at which point they can
wait and capture it. It is the same trade cloud images make. Say no
and =admin= gets ordinary, password-prompting =sudo= through =wheel=.
#+end_annotate

*** What it wrote

The answers land in one small file of shell variables:

#+attr_shortcode: :file /root/arch/host.env
#+begin_edit
HOSTNAME=myhost
DISK=/dev/disk/by-id/nvme-XP1000F256G_2213E5A1B2C3
ENCRYPT=no
SWAP_SIZE=8g
TIMEZONE=America/Denver
LOCALE=en_US.UTF-8
KEYMAP=us
ADMIN_NOPASSWD=yes
#+end_edit

Edit it with =vim /root/arch/host.env=, or run =setup host= again,
which re-asks every question with your current answers as the
defaults.

=/root/arch= is a git repository, and =setup host= seeds the rest of
it too:

| File                                     | Holds                                                     |
|------------------------------------------+-----------------------------------------------------------|
| =host.env=                               | The answers above                                         |
| =packages.txt=                           | Packages beyond the base set, which =setup= picks from the hardware |
| =units.txt=                              | systemd units to enable: =systemd-networkd=, =systemd-resolved=, =iwd=, =sshd=, =snapper-cleanup.timer= |
| =etc/systemd/network/*.network=          | DHCP on any wired (=en*=) and wireless (=wl*=) interface  |
| =etc/ssh/sshd_config.d/10-hardening.conf= | Keys only, no root login                                 |
| =etc/sudoers.d/10-admin=                 | Passwordless sudo for =admin=, if you said yes            |
| =etc/snapper/configs/root=, =etc/conf.d/snapper= | Snapshots of =/=, kept to the newest ten          |
| =bin/admin=                              | The =admin= command, installed to =/usr/local/bin=        |
| =aconfmgr/=                              | aconfmgr's view of all of the above, plus what to ignore  |
| =authorized_keys=                        | The SSH public keys =admin= will accept, copied from the stick |

Once seeded, these files are yours: =setup= never overwrites them,
except for the sudoers drop-in, which follows your answer about
passwordless sudo, and =aconfmgr/10-base.sh=, which =setup install=
rewrites from the hardware. The [[/arch-workstation/maintain][maintenance chapter]] explains =admin=
and =aconfmgr/=; until the machine is running you can ignore both.

*** Change anything before installing

Everything =setup install= puts on the machine beyond the base system
comes from those files, so this is where you deviate from the book.
Add packages to =packages.txt=. Add files under =etc/= and they are
installed at the same path under =/etc=. Add or remove units in
=units.txt=.

For example, to use NetworkManager instead of systemd-networkd and
iwd -- a perfectly good choice if you want its roaming and GUI
integration -- add =networkmanager= to =packages.txt=, replace the
first three lines of =units.txt= with =NetworkManager=, and delete
the two =.network= files. The aconfmgr configuration is worked out
from these files, so it follows without being edited. Commit when you
are done:

#+attr_shortcode: :style secondary :title Run this on the live system:
#+begin_run
git -C /root/arch commit -am "Use NetworkManager"
#+end_run

*** Reinstalling a machine you already have

If the machine has been installed this way before, its host repo
already exists -- inside the old installation at =~admin/arch=, and
anywhere you pushed it. Point =setup= at it instead of answering the
questions again:

#+attr_shortcode: :style secondary :title Run this on the live system:
#+begin_run
setup host --from git@git.example.com:you/arch-myhost.git
#+end_run

The live system has no private key of its own, so cloning a private
repo over SSH uses yours: connect with =ssh -A boomstick= to forward
your agent.

=--from= also takes a path to a =host.env= file, or a name, which is
looked up as =boomstick/hosts/<name>.env= on the stick's config
partition -- handy when the machine has no route to your git server.

The only answer it re-checks is the disk. A =by-id= name belongs to
one physical drive, so a reinstall onto a new drive -- the usual
reason for reinstalling -- has to pick again.

#+attr_shortcode: :style warning :title No secrets in the host repo
#+begin_notice
The host repo is meant to be pushed to a git remote, so it holds no
secrets. Passwords are asked for during =setup install= and written
nowhere else. WiFi passphrases are copied from the live system into
the target, never into the repo. The SSH keys it does hold are
/public/ keys. Even so, make any remote you push it to private: it
describes your machine in detail.
#+end_notice

** Prepare the disk
:PROPERTIES:
:EXPORT_FILE_NAME: disk
:EXPORT_HUGO_SLUG: disk
:END:

This is the first step that writes to the target machine. Up to now
everything lived in RAM and a power cycle undid it; this step
destroys whatever was on the disk you picked.

*** What it builds

A single GPT disk with two partitions:

| Partition | Size  | Format | Mounted at | Holds                                  |
|-----------+-------+--------+------------+----------------------------------------|
| 1         | 1 GiB | FAT32  | =/boot=    | The bootloader, kernel and initramfs   |
| 2         | rest  | btrfs  | =/= etc.   | Everything else, optionally encrypted  |

The same two partitions serve both architectures, for different
reasons. On an x86_64 PC the first is the *EFI System Partition* the
firmware reads. On a Raspberry Pi 5 it is the *firmware partition*,
where the Pi's bootloader expects =config.txt=, the kernel and the
device trees; the Pi ignores partition type codes and simply uses the
first FAT partition. A gibibyte is far more than one kernel needs, and
that is the point: boot partitions that are too small are a well-worn
regret.

Everything else goes on btrfs, split into *subvolumes*. A subvolume is
an independently mountable tree inside one filesystem: they all draw
from the same free space, so there is no sizing decision to regret,
but each can be snapshotted, mounted or rolled back on its own.

| Subvolume    | Mounted at              | Why it is separate                                         |
|--------------+-------------------------+------------------------------------------------------------|
| =@=          | =/=                     | The system itself -- the thing you roll back               |
| =@home=      | =/home=                 | Your data, which must /survive/ a rollback of the system   |
| =@snapshots= | =/.snapshots=           | Where snapshots are kept; cannot live inside =@=           |
| =@log=       | =/var/log=              | Logs of what went wrong should outlive the rollback        |
| =@pkg=       | =/var/cache/pacman/pkg= | A re-downloadable cache, not worth snapshotting            |
| =@swap=      | =/swap=                 | A swapfile cannot sit on a subvolume that gets snapshotted |
| =@nix=       | =/nix=                  | The Nix store, if you install the [[/arch-workstation/desktop][desktop]]: big, and Nix's own |

Every subvolume except =@swap= is mounted =noatime,compress=zstd:1=.
=noatime= stops a write on every /read/, which is pure write
amplification on a workstation. zstd at level 1 is fast enough to be
effectively free, while higher levels cost noticeably more CPU for a
few percent more space. =@swap= is mounted without compression,
because a swapfile must be a plain, uncompressed, un-copy-on-write
extent.

*** Run it

#+attr_shortcode: :style secondary :title Run this on the live system:
#+begin_run
setup disk
#+end_run

It reads the host file and shows you what it is about to destroy
before it destroys it:

#+begin_annotate
#+begin_src bash
================ Review =================
Host:         myhost
Disk:         /dev/disk/by-id/nvme-XP1000F256G_2213E5A1B2C3
              (nvme0n1 238.5G XP1000F256G)
Currently:    2 partition(s): nvme0n1p1 vfat ESP; nvme0n1p2 btrfs arch;
Will create:  1G ESP (vfat) + rest btrfs, no encryption
Subvolumes:   @ @home @snapshots @log @pkg @swap @nix
Swap:         8g swapfile
=========================================

This ERASES /dev/nvme0n1. Type the hostname to continue: myhost
#+end_src

The =Currently:= line is there so that you notice when the disk you
picked is not the one you thought it was -- on a machine you are
operating blind, over SSH, from another room, it is worth being slower
than feels necessary. Typing the hostname rather than =y= is
deliberate friction, and =--yes= does not answer it. To script it,
pass =--confirm-wipe myhost=.

Before it gets this far, =setup disk= refuses to run at all if the
machine booted in legacy BIOS mode, if any partition on the disk is
mounted or in use as swap, or if the disk is the stick itself.
#+end_annotate

Then it runs, echoing each command as it goes:

#+begin_stdout
+ sgdisk --zap-all /dev/nvme0n1
+ sgdisk --clear --new=1:0:+1G --typecode=1:ef00 --change-name=1:ESP --new=2:0:0 --typecode=2:8300 --change-name=2:root /dev/nvme0n1
+ partprobe /dev/nvme0n1
+ udevadm settle
+ wipefs --all --quiet /dev/nvme0n1p1 /dev/nvme0n1p2
+ mkfs.fat -F32 -n ESP /dev/nvme0n1p1
+ mkfs.btrfs --quiet -L arch /dev/nvme0n1p2
+ mount /dev/nvme0n1p2 /mnt
+ btrfs subvolume create /mnt/@
  ... six more subvolumes, then umount /mnt and the eight mounts
+ btrfs filesystem mkswapfile --size 8g --uuid clear /mnt/swap/swapfile
+ swapon /mnt/swap/swapfile

✓ disk       8 mounts under /mnt, 8g swap active
Next: setup install
#+end_stdout

Reading it across:

 - =sgdisk --zap-all= destroys the old GPT /and/ any leftover MBR.
   =--new=1:0:+1G= makes partition 1 a gibibyte from the first aligned
   sector, =--new=2:0:0= gives partition 2 the rest, and the type codes
   mark them as an EFI System Partition (=ef00=) and a Linux
   filesystem (=8300=).
 - =wipefs= is the step most install guides leave out. The new
   partitions start exactly where the old ones did, so on a reinstall
   the old btrfs signature is still sitting at the start of partition
   2, and =mkfs.btrfs= refuses to format over it.
 - The filesystem labels (=ESP=, =arch=) are a convenience: they make
   =lsblk= readable.
 - The subvolumes are created at the top level of the filesystem,
   which is then unmounted and never used again except as their
   container. =@= is mounted first, because the mount points for the
   others are directories inside it.
 - The ESP is mounted =fmask=0077,dmask=0077=, readable by root only,
   and =genfstab= carries that into the fstab. FAT has no permissions
   of its own, and with the default masks systemd-boot's random seed
   is world-readable, which =bootctl= reports at every boot as "a
   security hole".
 - The swap is turned on now, not just created, for two reasons: on a
   low-memory machine it is what keeps the install from running out,
   and the fstab is generated from what is /active/, so a swapfile that
   is not on would be silently left out of it.

#+attr_shortcode: :style info :title Page size on the Raspberry Pi
#+begin_notice
On the Pi, =mkswapfile= reports =page size 16384= rather than =4096=,
because =linux-rpi-16k= is built with 16 KiB pages. That is expected.
It does leave one trap: a swapfile records the page size it was made
with, and a kernel with a different page size refuses it. If you ever
move this disk to a generic 4 KiB-page arm64 kernel, =swapon= fails
with =Invalid argument=; delete the swapfile and make a new one.
#+end_notice

*** With encryption

If the host file says =ENCRYPT=yes=, two commands join the list before
=mkfs.btrfs=:

#+begin_stdout
+ cryptsetup luksFormat --type luks2 --batch-mode --verify-passphrase /dev/nvme0n1p2
+ cryptsetup open /dev/nvme0n1p2 cryptroot
#+end_stdout

The first asks you to set and confirm the passphrase; the second asks
for it again to unlock the container, which makes
=/dev/mapper/cryptroot= appear, and everything after that formats and
mounts the mapper device instead of the partition. LUKS2's defaults
are good ones -- =aes-xts-plain64=, and =argon2id= as the key
derivation function, which is memory-hard and therefore expensive to
attack with GPUs -- so =setup= does not choose any of them for you.

#+attr_shortcode: :style warning :title The passphrase cannot be recovered
#+begin_notice
There is no backdoor and no reset. If you forget it, the data is
gone -- that is the entire purpose. Put it in a password manager
before you reboot, not after.
#+end_notice

*** Running it again

If =/mnt= already holds the layout =setup disk= would build, it says
so and touches nothing:

#+begin_stdout
/mnt already has the layout for myhost. Nothing to do.
#+end_stdout

If the layout exists on the disk but is not mounted -- the live system
rebooted, or you are coming back to finish a half-done install --
=--mount= puts it back without formatting, unlocking LUKS first if
the host file says the disk is encrypted:

#+attr_shortcode: :style secondary :title Run this on the live system:
#+begin_run
setup disk --mount
#+end_run

That is also the rescue path for a machine that will not boot: boot
the stick, run =setup host --from ...= and =setup disk --mount=, and
=arch-chroot /mnt= puts you inside it.

** Install the system
:PROPERTIES:
:EXPORT_FILE_NAME: install
:EXPORT_HUGO_SLUG: install
:END:

The disk is partitioned, formatted and mounted under =/mnt=, and there
is nothing on it. This step puts a complete Arch system there, makes
it able to boot itself, and makes sure you can log in when it does.

#+attr_shortcode: :style secondary :title Run this on the live system:
#+begin_run
setup install
#+end_run

#+begin_annotate
#+begin_src bash
================ Review =================

Detected:     x86_64 PC, UEFI

              + packages.txt: just tmux

#+end_src

Everything on this screen was decided either by the hardware or by
the host repo. If any of it is not what you want, answer =n=, change

#+end_annotate

#+attr_shortcode: :style info :title The same screen on a Raspberry Pi
#+begin_notice
Three lines read differently on a Pi 5, because they are the three
things chosen by the hardware:

#+begin_src bash
Detected:     Raspberry Pi 5 (aarch64, bcm2712)
Packages:     ... snapper snap-pac linux-rpi-16k firmware-raspberrypi linux-firmware
Boot:         Pi firmware (cmdline.txt)
#+end_src

=linux-rpi-16k= and =firmware-raspberrypi= replace =linux= and the
=intel-ucode= / =amd-ucode= microcode, and there is no bootloader to
install. Everything else -- the subvolumes, the accounts, the units,
the host repo, the maintenance tools -- is the same on both.
#+end_notice

After you confirm, it works through eleven stages. Apart from the
passwords near the end, it asks nothing more.

*** 1. Packages

=setup= refreshes the live system's pacman keyring, then installs the
base set and everything in =packages.txt= into =/mnt= with =pacstrap=
-- pacman pointed at a different root. There is no image and no magic:
when it finishes, =/mnt= is an ordinary directory tree that happens to
be a Linux system.

The base set is chosen from the hardware:

| Package                     | Why it is there                                                     |
|-----------------------------+---------------------------------------------------------------------|
| =base=                      | The minimum system: glibc, bash, coreutils, pacman, systemd          |
| =linux= / =linux-rpi-16k=   | A kernel, which =base= does not include; picked by =uname -m=, and on aarch64 only for a =bcm2712= board |
| =linux-firmware=            | Firmware blobs for WiFi, GPUs and other devices                      |
| =firmware-raspberrypi=      | Pi only: VideoCore firmware and the files its bootloader reads       |
| =intel-ucode= / =amd-ucode= | x86_64 only, by CPU vendor: microcode errata fixes, loaded at boot   |
| =btrfs-progs=               | The root filesystem is btrfs and cannot be checked without it        |
| =cryptsetup=                | Always: a couple of megabytes, and forgetting it on an encrypted disk is a far worse afternoon |
| =sudo=                      | Administration from =admin=                                          |
| =openssh=                   | The whole point of a headless machine                                |
| =iwd=                       | WiFi                                                                 |
| =vim=                       | An editor that exists inside the installed system                    |
| =less=                      | git's pager. Only an /optional/ dependency of git, so without it =git log= in the host repo fails outright rather than merely not paging |
| =git=                       | The host repo is a git repository                                    |
| =pacutils=, =expect=        | What aconfmgr needs to compare the machine with the repo             |
| =snapper=, =snap-pac=       | Snapshots of =/=, and the pacman hooks that take them                |

The keyring refresh matters more than it looks. Every package is
checked against developer signing keys, and the copy of those keys on
the stick is as old as the image; a stick that has been in a drawer
for six months will eventually meet a package signed by a key it has
never heard of. The resulting error names a signature rather than a
stale keyring, which sends people down the wrong path.

pacstrap uses the live system's mirror list, which by default starts
with Arch's own geo-routed CDN -- a fine first choice anywhere. If you
would rather draw from a measured-fastest mirror near you, run
=reflector --country US --protocol https --age 12 --sort rate --save
/etc/pacman.d/mirrorlist= before =setup install= (x86_64 only;
reflector is not on the Pi image and knows nothing about Arch Linux
ARM's mirrors).

#+attr_shortcode: :style warning :title On an older Pi stick
#+begin_notice
Early BOOMSTICK Pi images shipped without Arch Linux ARM's signing
keys, and on one of those every ALARM package -- including the
kernel -- fails as =unknown trust=. =setup= checks before it starts,
and stops with the fix: rebuild the stick, or sign the key locally
with =pacman-key --lsign-key 68B3537F39A313B3E574D06777193F152BDBE6A6=.
On such a stick it also runs =pacstrap= without =-K=, because =-K=
gives the target a fresh keyring and would leave that hand-made trust
behind.
#+end_notice

On a re-run, when the base system is already there, this stage only
installs what is missing.

*** 2. fstab

The new system needs to know how to mount its own filesystems at boot,
and right now that knowledge exists only in the live system's mount
table, which is what =genfstab -U= reads. =-U= writes UUIDs rather
than device paths, because =/dev/sda= is assigned in whatever order
the kernel finds disks, while a UUID belongs to the filesystem and
never moves.

=setup= /writes/ the file rather than appending to it, so running it
twice cannot duplicate an entry, and it stops if the swapfile is
missing from the result.

*** 3. Time zone, locale, keymap and hostname

=/etc/localtime= becomes a symlink into =/usr/share/zoneinfo=, and the
hardware clock is set from the system clock. Your locale is uncommented
in =/etc/locale.gen= and generated, and written to =/etc/locale.conf=
as the default. The keymap goes into =/etc/vconsole.conf= and the
hostname into =/etc/hostname=. There is no need for a =127.0.1.1=
line in =/etc/hosts=: systemd's =myhostname= resolver answers for the
local hostname already.

#+attr_shortcode: :style info :title Clocks on the Raspberry Pi
#+begin_notice
A Pi 5 has a real-time clock, but it only keeps time across a power
cut if you have fitted the optional battery. Without one it boots
with a meaningless date and waits for NTP to correct it, which is
harmless as long as the network comes up. The same is true of the
live system, and a wrong clock makes pacman's signature checks and
TLS fail in confusing ways -- so if =setup install= fails on
signatures on a Pi, check =timedatectl= first.
#+end_notice

*** 4. initramfs

To mount the root filesystem the kernel needs drivers -- for the disk
controller, for btrfs, maybe for unlocking LUKS -- and those drivers
live on the root filesystem it cannot mount yet. The initramfs is a
second, tiny filesystem loaded into memory alongside the kernel with
just enough in it to find the real root, mount it and hand over.
Arch builds it with =mkinitcpio=.

The default =HOOKS= are already right for an unencrypted btrfs root,
including the =microcode= hook that folds CPU microcode into the
image (which is why the boot entry below has no separate
=intel-ucode.img= line, unlike older guides). On an encrypted disk
=setup= adds =sd-encrypt= after =block=. It has to be =sd-encrypt=,
not plain =encrypt=: the default initramfs is systemd-based, and the
older hook builds without complaint into an image that cannot unlock
the disk.

=mkinitcpio -P= then rebuilds every image. Warnings about missing
firmware for hardware you do not have are normal.

*** 5. Bootloader

A machine can only start itself if three things line up: the firmware
finds something to run, that something loads a kernel and the
initramfs, and the kernel is told where its root filesystem is. The
last part is where installs usually fail, and they fail the same way:
the machine powers on, prints a little, and drops to an emergency
shell.

On an *x86_64 PC*, =setup= runs =bootctl install=, which copies
[[https://wiki.archlinux.org/title/Systemd-boot][systemd-boot]] onto the ESP and registers it with the firmware, then
writes its menu and one entry:

#+attr_shortcode: :file /boot/loader/loader.conf
#+begin_edit
default  arch.conf
timeout  3
console-mode keep
editor   no
#+end_edit

#+attr_shortcode: :file /boot/loader/entries/arch.conf
#+begin_edit
title   Arch Linux
linux   /vmlinuz-linux
initrd  /initramfs-linux.img
options root=UUID=e1445380-51a2-449d-ad82-8ac3286cbfb6 rootflags=subvol=@ rw
#+end_edit

=editor no= matters more than it looks: with the editor enabled,
anyone at the keyboard can append =init=/bin/sh= to the kernel command
line and get a root shell without a password.

On a *Raspberry Pi 5* there is no bootloader to install. The Pi's
firmware reads =config.txt= and =cmdline.txt= from the FAT partition,
loads the kernel and initramfs itself, and jumps straight in.
=config.txt= already loads the initramfs, so =setup= leaves it alone
and rewrites only the kernel command line, which ships pointing at an
SD card:

#+attr_shortcode: :file /boot/cmdline.txt
#+begin_edit
root=UUID=e1445380-51a2-449d-ad82-8ac3286cbfb6 rootflags=subvol=@ rw rootwait console=serial0,115200 console=tty1 fsck.repair=yes
#+end_edit

The firmware reads only the /first line/ of that file, so if you edit
it by hand, make sure your editor has not wrapped it. =rootwait= tells
the kernel to wait for a USB or NVMe disk to appear rather than give
up. Both files are pacman /backup/ files of the kernel package, so a
kernel update keeps your version and writes its own alongside as
=cmdline.txt.pacnew= -- which is how new firmware options arrive, and
why =.pacnew= files are worth checking after kernel updates.

Either way, the part that is specific to this book's layout is
=rootflags=subvol=@=. Without it the kernel mounts the /top/ of the
btrfs filesystem, finds the subvolumes sitting there as directories,
and fails to boot. The UUID is read from the filesystem =setup disk=
made, never typed. On an encrypted disk, the root becomes
=rd.luks.name=<LUKS UUID>=cryptroot root=/dev/mapper/cryptroot= --
the UUID of the LUKS /container/, which is a different UUID from the
btrfs filesystem inside it, and the easiest thing to get wrong when
doing this by hand.

#+attr_shortcode: :style warning :title The Pi half is untested
#+begin_notice
The x86_64 half of this stage boots in BOOMSTICK's test VM, encrypted
or not: =ENCRYPT=yes just test-vm= installs onto LUKS, answers the
initramfs passphrase prompt on the serial console, and logs in
afterwards. The Raspberry Pi half -- =cmdline.txt=, and a passphrase
prompt with no bootloader behind it -- has not yet booted a machine.
#+end_notice

*** 6. The host repo, applied

The files under the host repo's =etc/= are installed at the same paths
under =/mnt/etc=, owned by root. git does not keep file modes, so
=setup= sets them by place: =0440= for sudoers drop-ins, which =sudo=
insists on before it will read them, and =0644= for everything else.
Files under the repo's =bin/= -- =admin= -- go to =/usr/local/bin=,
mode =0755=. Then every unit in =units.txt= is enabled.

Enabling works inside the chroot because it only creates symlinks on
disk. Nothing /starts/ until the machine reboots: the =systemd= you
can see from the chroot belongs to the live system, not the target.

The network this sets up by default is *systemd-networkd* for
addresses, *systemd-resolved* for DNS and *iwd* for WiFi -- the same
combination the live system is running. The two =.network= files
match by name prefix (=en*=, =wl*=) rather than exact name, so they
work on any machine without checking what the kernel called the
hardware, and a USB ethernet adapter plugged in later just works.

The sshd drop-in is three lines, and all three matter.
=PasswordAuthentication no= alone is not enough: with PAM,
keyboard-interactive is a second route to the same password prompt,
so it is switched off explicitly, along with root login. Arch's
=sshd_config= includes =/etc/ssh/sshd_config.d/*.conf=, so the drop-in
overrides the defaults without touching the shipped file, and package
updates never conflict with it.

*** 7. The live system's side

Two things can only be done from outside the chroot, so =setup= does
them from the live system against =/mnt=:

 - =/etc/resolv.conf= becomes a symlink to resolved's stub. Inside the
   chroot that file is the live system's own, bind-mounted over the
   target's so that package downloads can resolve names, and replacing
   it there fails.
 - The live system's iwd network files -- the WiFi passphrases the
   stick joined with -- are copied into =/mnt/var/lib/iwd=. This is the
   single most commonly forgotten step of a headless install: the
   machine boots, the disk is perfect, and it never joins the network
   because nothing told it the passphrase.

*** 8. Accounts

=admin= and =user= are created, if they do not exist yet, with
=admin= in =wheel=. =visudo -c= then checks that the whole sudo
configuration parses. That check is not optional: a malformed sudoers
file does not degrade gracefully -- =sudo= refuses to run at all --
and on a machine where =sudo= is the only route to root, that is a
lockout you can only fix from the console.

=admin='s =~/.ssh/authorized_keys= is installed from the host repo,
owned by =admin=, mode =0600=, in a =0700= directory. Those modes are
not decoration: sshd silently refuses an =authorized_keys= file that
other users could write to, and from the client's side you are just
asked for a password that will never be accepted.

The daily user is given the same keys, so the first thing you do on the
new machine can be logging in as yourself rather than as its
administrator. The two are managed differently from then on:
=admin='s are installed from the repo on every run, because the repo is
what says who may administer this machine, while the daily user's are
/seeded once/ and left alone afterwards -- a key added there by hand is
theirs, and a re-run will not revert it.

*** 9. Passwords

The only prompts after the review: a password for =admin= and one for
the daily user, each typed twice. On a re-run, an account that already
has one is skipped.

=root= is not among them. It is *locked* instead -- no password at all,
so there is none to guess, leak, or forget to rotate. Nothing needs it:
=admin= is in =wheel=, administration happens through =sudo=, and sshd
refuses root whatever its password is. =setup check= expects
=root=L=.

#+attr_shortcode: :style warning :title What a locked root costs
#+begin_notice
systemd's emergency and rescue targets ask for the root password, and
=sulogin= will not open a shell for a locked account -- it says so and
reboots. A machine that cannot mount its root filesystem therefore
cannot be rescued from its own keyboard.

This book makes that trade on purpose, because the stick is the
recovery tool and a better one: boot it, then =setup host --from= and
=setup disk --mount= as in [[/arch-workstation/setup/disk][Prepare the disk]], and =arch-chroot /mnt=
gives you a root shell inside the broken system -- over SSH, which a
keyboard attached to a machine in another room does not offer.

If you would rather have the console, =sudo passwd root= on the running
machine sets one. =setup check= accepts a root password that exists; it
objects only to an account with none.
#+end_notice

*** 10. aconfmgr

[[https://github.com/CyberShadow/aconfmgr][aconfmgr]] is what =admin= runs. It is in neither Arch's nor Arch Linux
ARM's repositories -- only the AUR has it, and building AUR packages
would mean =base-devel= on every machine -- but it is a bash program
with no compiled parts, so =setup= clones it from GitHub at a fixed
commit into =/usr/local/lib/aconfmgr=, and links it where its own
launcher looks (=/usr/lib/aconfmgr=, =/usr/local/bin/aconfmgr=).
Pinning the commit means every machine runs the version this book was
checked against; a newer one is a deliberate change to =setup=.

*** 11. The host repo moves in

=setup= writes =aconfmgr/10-base.sh=, the base packages it picked for
this hardware, so aconfmgr knows them as wanted. A commit records the
install in the host repo, which is then copied to
=/mnt/home/admin/arch= and handed to =admin=. From the first boot,
the description of the machine lives on the machine.

=setup install= finishes by running the [[/arch-workstation/setup/check][check]].

** A tunnel of its own (optional)
:PROPERTIES:
:EXPORT_FILE_NAME: wireguard
:EXPORT_HUGO_SLUG: wireguard
:END:

The stick comes up on WireGuard by itself, which is most of why
installing a headless machine from your desk works at all. The machine
you have just installed can do the same -- and the moment to arrange it
is now, before it reboots, because afterwards it is on its own.

#+attr_shortcode: :style secondary :title Run this on the live system:
#+begin_run
setup wireguard
#+end_run

#+attr_shortcode: :style warning :title Not the stick's key
#+begin_notice
Do not copy =wg0.conf= off the stick. That key /is/ the stick's
identity to your server, and a second machine holding it would be a
second peer claiming to be the same one -- a confusing afternoon
waiting to happen. The stick's job is to install machines; this machine
gets a key of its own.
#+end_notice

*** Where the key comes from

The first question is how the key should come about, and the default is
the careful answer.

#+begin_annotate
#+begin_src bash
  genkey -- make the key here, so your provider never sees it
  paste  -- you already have a wg0.conf, private key included
? Key: genkey
#+end_src

=genkey= makes the key pair on the live system and prints only the
/public/ half. You give that to your VPN provider, or add it as a
=[Peer]= on your own server, and paste back the configuration it hands
you. =setup= splices the private key into it -- over a placeholder
=PrivateKey= line if there is one, or under =[Interface]= if there is
not. The secret never leaves the machine it belongs to.

=paste= is for when you already hold a complete =wg0.conf=, private key
and all, because that is what you were given.
#+end_annotate

Either way the configuration is pasted at the terminal and ends with
Ctrl-D, so there is no file to edit on a machine that is still being
installed:

#+begin_stdout
This machine's public key -- give this to your provider, or add it
as a peer on your own server. The private key stays here.

    IUpvRDOi8yIS4VER07dIOLXYJC9/9mo4OTJp2RMcqAM=

Now paste the configuration they give you back.
  (paste it, then press Ctrl-D on a line of its own)
#+end_stdout

*** What it writes

#+begin_stdout
================ Review =================
Address:      10.9.0.7/32
Endpoint:     vpn.example.com:51820
AllowedIPs:   10.9.0.0/24
DNS:          10.9.0.1
Keepalive:    25
PrivateKey:   (not shown, and never written to the repo)
Writes:       /mnt/etc/wireguard/wg0.conf, 0600 root:root
=========================================
#+end_stdout

The key goes to the target's =/etc/wireguard/wg0.conf=, owned by root
and readable by nobody else, and =aconfmgr/90-ignore.sh= gains
=IgnorePath '/etc/wireguard/*'= beside the rule that already ignores
the SSH host keys. So =admin diff= does not report it as drift, and it
is never committed.

What /is/ configuration goes in the host repo, where the rest of the
machine's description lives: =wireguard-tools= in =packages.txt= and
=wg-quick@wg0= in =units.txt=. Either order works: if this step runs
before [[/arch-workstation/setup/install][Install the system]] the install picks both up, and if it runs
after -- where the step order puts it -- it installs the package and
enables the unit itself.

#+attr_shortcode: :style info :title A DNS line needs one more package
#+begin_notice
If the configuration has a =DNS == line, =wg-quick= hands it to
=resolvconf=, which the installed system does not have: =base= does not
bring it and the live system's copy comes from the ISO. =setup= adds
=systemd-resolvconf= to =packages.txt= when it sees one, which is the
difference between a tunnel that comes up and a unit that fails on
first boot.
#+end_notice

#+attr_shortcode: :style warning :title Nothing is echoed back
#+begin_notice
The review names the address, the endpoint, the AllowedIPs, the DNS and
the keepalive, and of the key says only that it is not shown. That is
deliberate: everything =setup= prints is written to
[[/arch-workstation/setup/install][=logs/000_SETUP.txt=]] in the host repo and committed, so printing the
configuration would commit a private key. What you paste is echoed by
your terminal, not by =setup=, so it stays out of the log too.
#+end_notice

The tunnel comes up on the next boot. Check it there with =wg show=.

** Check and reboot
:PROPERTIES:
:EXPORT_FILE_NAME: check
:EXPORT_HUGO_SLUG: check
:END:

Every step so far fails loudly if it fails at all. The last way an
install goes wrong fails quietly: the machine reboots, comes up
perfectly -- and does not let you in, because there is no account, or
no network, or sshd was never enabled. On a headless box in another
room, that means fetching a monitor and a keyboard. The check exists
so that you find out before the reboot rather than after.

#+attr_shortcode: :style secondary :title Run this on the live system:
#+begin_run
setup check
#+end_run

#+begin_stdout
✓ hostname   myhost
✓ fstab      8 entries + swap, no duplicates
✓ boot       systemd-boot, entries/arch.conf: root=UUID=e1445380-51a2-449d-ad82-8ac3286cbfb6
✓ initramfs  initramfs-linux.img
✓ accounts   admin user
✓ passwords  root=L admin=P user=P
✓ sudo       visudo -c OK
✓ units      systemd-networkd systemd-resolved iwd sshd snapper-cleanup.timer enabled
✓ ssh        3 key(s) for admin, sshd config parses
✓ admin      aconfmgr 96ab414, snapper config root
✓ wifi       1 network(s) in /var/lib/iwd
All checks passed. Safe to reboot: setup reboot
#+end_stdout

| Line        | Fails when                                                                                  |
|-------------+---------------------------------------------------------------------------------------------|
| =hostname=  | =/etc/hostname= does not match the host file                                                |
| =fstab=     | fewer entries than subvolumes plus the ESP, a duplicated mount point, or no swap line when there should be one |
| =boot=      | the systemd-boot entry or =cmdline.txt= lacks =rootflags=subvol=@=, or =cmdline.txt= is more than one line |
| =initramfs= | there is no initramfs image in =/boot=                                                      |
| =accounts=  | =admin= or =user= does not exist                                                            |
| =passwords= | =admin= or the daily user is not =P= (set), or =root= is =NP=: no password at all. =root=L= is what setup leaves, and =root=P= is allowed |
| =sudo=      | =visudo -c= fails                                                                           |
| =units=     | anything in =units.txt= is not enabled                                                      |
| =ssh=       | =admin= has no keys, the file has the wrong owner or mode, or =sshd -t= rejects the config   |
| =admin=     | aconfmgr, =/usr/local/bin/admin= or snapper's root configuration is missing                 |
| =wifi=      | there are no WiFi credentials /and/ no ethernet interface: it would never join a network   |

Any =✗= means a machine that will not come back, and =setup check=
exits non-zero. One thing it reports as fine looks like an error if
you run =sshd -t= yourself: =no hostkeys available=. The installed
system has no host keys yet -- it generates its own on first boot --
and sshd only looks for them after the configuration has parsed.

*** Reboot

#+attr_shortcode: :style secondary :title Run this on the live system:
#+begin_run
setup reboot
#+end_run

That runs the check again and only if it passes does it =swapoff=,
=umount -R /mnt=, close the LUKS volume if there is one, and reboot.
There is no flag to skip the check.

Pull the stick out once the machine has powered down, or it will boot
the installer again.

*** Connecting to the new machine

The installed system is a *different host* from the stick, and it
will say so: its SSH host keys are its own, unrelated to the ones on
the USB stick, so the =boomstick= entry in your SSH config does not
describe it. Give it an entry of its own:

#+attr_shortcode: :file ~/.ssh/config
#+begin_edit
Host myhost
    HostName 192.168.1.50
    User admin
#+end_edit

#+attr_shortcode: :style secondary :title Run this on your workstation:
#+begin_run
ssh myhost
#+end_run

You will be asked to accept a new host key, which is correct -- this
really is a machine you have never spoken to before. The address may
have changed too: the machine is asking for its own DHCP lease now,
under its own hostname.

#+attr_shortcode: :style tip
#+begin_notice
If it does not answer, check first whether it is on the network at
all -- look at your router's lease table, or =ping= it. A machine that
has an address but refuses SSH is a different problem from one that
never appeared, and they want opposite kinds of investigation. For
the second kind, boot the stick again: =setup host --from= and =setup
disk --mount= get you back into the installed system with
=arch-chroot /mnt=.
#+end_notice

Once you are in as =admin=, the install is finished. From here on the
machine is looked after with =admin=, in [[/arch-workstation/maintain][Keeping it maintainable]],
starting with pushing its host repo somewhere off the machine.

** Keeping it maintainable
:PROPERTIES:
:EXPORT_FILE_NAME: _index
:EXPORT_HUGO_SLUG: _index
:EXPORT_HUGO_WEIGHT: 500
:END:

The introduction made a promise about Arch: the running system is the
source of truth, it drifts, and nothing but your own discipline
records how it got that way. This chapter is that discipline, written
down as a git repository and one command, so that it does not have to
live in your head.

Log in as =admin=. The host repo that =setup= built the machine from
is already there:

#+attr_shortcode: :style secondary :title Run this on the new machine:
#+begin_run
cd ~/arch
git log --oneline
#+end_run

#+begin_stdout
3f9c2e1 setup install: myhost (x86_64 PC, UEFI)
a14b07d setup host: myhost
#+end_stdout

| File                  | Holds                                                    | Changed by           |
|-----------------------+----------------------------------------------------------+----------------------|
| =host.env=            | The install answers                                      | You, rarely          |
| =packages.txt=        | Every package you asked for, beyond the base set         | You                  |
| =units.txt=           | Every unit you enabled                                   | You                  |
| =etc/=                | Your files under =/etc=                                  | You                  |
| =bin/admin=           | The =admin= command itself                               | Nobody, usually      |
| =authorized_keys=     | Public keys =admin= accepts                              | You                  |
| =aconfmgr/=           | The same, in aconfmgr's terms, plus what to ignore       | Nobody, usually      |
| =aconfmgr/10-base.sh= | The base packages =setup= picked for this hardware       | =setup install=      |

=admin= runs [[https://github.com/CyberShadow/aconfmgr][aconfmgr]] against =~/arch/aconfmgr=:

| Command         | Direction        | What it does                                                         |
|-----------------+------------------+----------------------------------------------------------------------|
| [[/arch-workstation/maintain/diff][admin diff]]      | look only        | Lists every difference between the machine and the repo              |
| [[/arch-workstation/maintain/save][admin save]]      | machine → repo   | Writes the machine's drift into the repo, for you to sort and commit |
| [[/arch-workstation/maintain/save][admin apply]]     | repo → machine   | Makes the machine match the repo, removals included                  |
| [[/arch-workstation/maintain/upgrade][admin upgrade]]   | both             | Refuses on drift, =pacman -Syu=, apply, reports =.pacnew= files       |
| =admin git ...=   | the repo itself  | Runs git in the host repo, from wherever you are                     |

=admin git= saves remembering where the repo lives: =admin git log=,
=admin git commit -am "..."=, =admin git push=, from any directory.
Everything after =git= is handed to git untouched, and git's exit
status comes back, so =admin git diff --quiet= still works as a test.

=admin help= prints the same list. Every command takes aconfmgr's own
options after it: =--yes= answers its questions, =--skip-checksums=
skips comparing package files with their checksums, which is much
faster but misses edits to files that packages own.

*** What aconfmgr looks at

aconfmgr knows the whole system, not only what you told it about. It
lists the packages installed /explicitly/ (=pacman -Qe=; dependencies
come and go with them and are never listed), every file on the
system that no package owns, and every file a package owns that has
changed since it was installed. Anything in that list that the
configuration does not describe, or that the configuration describes
and the machine lacks, is drift.

A fresh install has no drift. That is not an accident of a new
system -- a fresh Arch install is full of files no package owns -- but
the result of =~/arch/aconfmgr/=, which accounts for all of them:

| File             | Describes                                                                                          |
|------------------+----------------------------------------------------------------------------------------------------|
| =00-helpers.sh=  | The helpers the others use, including one that works out the links =systemctl enable= makes           |
| =10-base.sh=     | The base packages for this hardware (written by =setup install=)                                    |
| =20-host.sh=     | What =setup= wrote from =host.env=: hostname, locale, keymap, time zone, =resolv.conf=               |
| =30-repo.sh=     | =packages.txt=, the files under =etc/= and =bin/=, and the units in =units.txt=                      |
| =40-system.sh=   | What packages and boot leave behind: units they enable, directories they make, aconfmgr's links      |
| =90-ignore.sh=   | What is not configuration at all                                                                    |

They are bash, read by aconfmgr in order. =20-host.sh= and
=30-repo.sh= do not copy anything: they /read/ =host.env=,
=packages.txt=, =units.txt=, =etc/= and =bin/=, so those stay the
files you edit and aconfmgr follows them. Adding a package is still a
line in =packages.txt=.

*** What is ignored, and why

=90-ignore.sh= lists what aconfmgr should not report:

 - *What =setup= owns*: =/boot= (the bootloader, kernel and initramfs,
   rewritten by pacman hooks) and =/etc/fstab= (UUIDs of this disk).
 - *Accounts*: =/etc/passwd=, =group=, =shadow= and friends. =setup=
   makes the accounts, and password hashes never go into the repo.
 - *Secrets and identity*: SSH host keys, =/etc/machine-id=, pacman's
   keyring.
 - *Generated files*: the CA bundle, =ld.so.cache=, module and hardware
   databases, the locale archive, the mirror list.
 - *State*: =/var/lib=, =/var/log=, =/var/tmp=, =/swap=, =/.snapshots=,
   the Nix store (=/nix=), and aconfmgr's own checkout.

aconfmgr already ignores =/home=, =/root=, =/tmp=, =/var/cache= and
the pseudo-filesystems. When something new shows up that is state
rather than configuration -- a database a service keeps under =/srv=,
say -- the fix is a line here, with its reason:

#+attr_shortcode: :file ~/arch/aconfmgr/90-ignore.sh
#+begin_edit
# The music server's library database.
IgnorePath '/srv/music/*.db'
#+end_edit

Quote the pattern, or bash expands it before aconfmgr sees it.

*** Push it somewhere

The host repo is the only record of this machine that exists off its
own disk -- or it will be, once you push it. The next reinstall starts
from it with =setup host --from=. Make it a *private* repository: it
holds no secrets, but it describes your machine in detail.

#+attr_shortcode: :style secondary :title Run this on the new machine:
#+begin_run
git -C ~/arch remote add origin git@git.example.com:you/arch-myhost.git
git -C ~/arch push -u origin main
#+end_run

** See what drifted
:PROPERTIES:
:EXPORT_FILE_NAME: diff
:EXPORT_HUGO_SLUG: diff
:END:

#+attr_shortcode: :style secondary :title Run this on the new machine:
#+begin_run
admin diff
#+end_run

On a machine that matches its repo:

#+begin_stdout
No drift: the machine matches /home/admin/arch.
#+end_stdout

After installing =htop= and dropping a sysctl file into =/etc= by hand:

#+begin_stdout
Drift (as the aconfmgr lines that would describe it):
  AddPackage htop # Interactive process viewer
  CopyFile /etc/sysctl.d/99-swappiness.conf
#+end_stdout

Each line is what aconfmgr would have to add to the configuration to
describe the machine as it is. Removals show up the same way, as
=RemovePackage= or =RemoveFile=: something the repo has and the
machine lost.

=admin diff= runs =aconfmgr save= into a throwaway copy of
=~/arch/aconfmgr=, so it changes nothing, and it exits 1 when there is
drift -- a reasonable thing to run from a timer and send to the same
webhook the BOOMSTICK uses. aconfmgr prints its progress to stderr as
it goes; it reads every file on the system, so expect it to take a
minute or two.

** Save and apply
:PROPERTIES:
:EXPORT_FILE_NAME: save
:EXPORT_HUGO_SLUG: save
:END:

Every line of drift has two possible fixes: change the repo to match
the machine, or change the machine to match the repo. =admin save= and
=admin apply= are the two.

*** Change the repo: admin save

When the drift is something you meant, record it:

#+attr_shortcode: :style secondary :title Run this on the new machine:
#+begin_run
admin save
#+end_run

#+begin_stdout
Wrote /home/admin/arch/aconfmgr/99-unsorted.sh. Move what you meant into a numbered
file, delete the rest (and 'admin apply' to undo it), then commit.
#+end_stdout

=99-unsorted.sh= holds the same lines =admin diff= printed. Files it
copied -- the sysctl file, here -- are under =aconfmgr/files/=. It is
git-ignored on purpose: it is a to-do list, not configuration, and it
should not survive the review.

*** Review and commit

Sort each line into the place it belongs. In this repo, that is
usually /not/ another aconfmgr file, but the plain file aconfmgr
reads:

| Line in 99-unsorted.sh         | Where it goes                                                              |
|--------------------------------+----------------------------------------------------------------------------|
| =AddPackage foo=               | =foo= on a line of =packages.txt=                                           |
| =CopyFile /etc/...=            | the file, moved from =aconfmgr/files/etc/...= to =etc/...=                  |
| =CreateLink /etc/systemd/...=  | the unit in =units.txt=                                                    |
| anything that is state         | an =IgnorePath= in =aconfmgr/90-ignore.sh=                                  |
| anything you did not mean      | nowhere: delete it, and =admin apply= will undo it on the machine           |

For the example above:

#+attr_shortcode: :style secondary :title Run this on the new machine:
#+begin_run
cd ~/arch
echo htop >> packages.txt
mkdir -p etc/sysctl.d
mv aconfmgr/files/etc/sysctl.d/99-swappiness.conf etc/sysctl.d/
rm -r aconfmgr/99-unsorted.sh aconfmgr/files
admin diff
git add -A
git commit -m "htop; lower swappiness"
#+end_run

The second =admin diff= is the check that the sorting was right: it
should say there is no drift. =save= writes and never commits, and
that review is the whole point -- it is the moment the machine's
history gets a reason attached to it.

*** Change the machine: admin apply

Edit the repo, commit, and apply:

#+attr_shortcode: :style secondary :title Run this on the new machine:
#+begin_run
echo ripgrep >> ~/arch/packages.txt
git -C ~/arch commit -am "Add ripgrep"
admin apply
#+end_run

aconfmgr shows each change before it makes it and asks. It installs
what is missing, puts files back the way the repo has them, and
enables units.

#+attr_shortcode: :style warning :title apply removes things too
#+begin_notice
=apply= makes the machine match the repo /exactly/. A package
installed by hand and not in =packages.txt= is uninstalled (aconfmgr
marks it as a dependency, then removes orphans); a file that the repo
does not describe and =90-ignore.sh= does not ignore is deleted. That is what makes it an undo button, and also why you
should run =admin diff= first and =admin save= anything you want to
keep. Read what it proposes before answering yes, and do not get into
the habit of =admin apply --yes=.
#+end_notice

This is also how a second machine picks up a change: pull the repo
there and apply.

*** Packages from the AUR

The [[https://wiki.archlinux.org/title/Arch_User_Repository][AUR]] is not a repository of packages but of /build recipes/,
contributed by users and reviewed by nobody. Nothing in =packages.txt=
can come from it, because =pacstrap= and =pacman= only know the
official repositories. aconfmgr calls anything pacman did not install
from a repository a *foreign* package, and describes it with a
=--foreign= flag:

#+attr_shortcode: :file ~/arch/aconfmgr/50-packages.sh
#+begin_edit
AddPackage --foreign yay          # Yet another yogurt. Pacman wrapper and AUR helper written in go.
AddPackage --foreign solo2-cli    # A CLI for SoloKeys Solo 2 devices
#+end_edit

You rarely type those lines yourself. Install something from the AUR by
hand and =admin save= writes them for you, comment and all, exactly as
it does for a package from the repos -- which is the point: a foreign
package that is not described is drift, and =admin apply= would remove
it.

What makes this work without any setting of your own is how aconfmgr
finds a builder. It looks for =aurman=, =pacaur=, =yaourt=, =yay=,
=paru=, =aura= and then =makepkg=, in that order, and uses the first
one on =PATH=; =--aur-helper HELPER= overrides the choice. And if one of
those names is itself in the list of foreign packages it is about to
install, it builds /that/ one first, with =makepkg=, and then uses it
for the rest. So a single =AddPackage --foreign yay= bootstraps itself
on a machine that has never had an AUR helper.

#+attr_shortcode: :style warning :title base-devel is not installed
#+begin_notice
=makepkg= is what every one of those helpers ultimately runs, and it
needs the toolchain in =base-devel= -- which =setup= does not install,
because a machine that builds nothing does not need a compiler. Add it
before the first foreign package, or the build fails on a missing
=fakeroot=:

#+begin_src bash
echo base-devel >> ~/arch/packages.txt
#+end_src

=makepkg= also refuses to run as root, which is why =admin apply= runs
aconfmgr as =admin= and lets it call =sudo= for the parts that need it.
#+end_notice

#+attr_shortcode: :style warning :title admin upgrade does not upgrade them
#+begin_notice
=admin upgrade= runs =pacman -Syu=, which has never heard of the AUR,
and then =admin apply=, which installs foreign packages that are
/missing/ but does not rebuild ones that are merely out of date. So
foreign packages stay at whatever version you built, including when
that version grows a security hole. Upgrading them is a separate habit
-- =yay -Sua= -- and the honest reason to keep the =--foreign= list
short.
#+end_notice

#+attr_shortcode: :style info :title Untested
#+begin_notice
No machine built by this book has installed an AUR package yet. The
behaviour above is read from the pinned aconfmgr (=96ab414=) rather
than observed.
#+end_notice

One command for the thing you will do most often, in an order worth
not having to remember:

 1. Refuse to start if =admin diff= reports drift. Upgrading a machine
    you cannot describe makes it harder to describe. =admin save= or
    =admin apply= first.
 2. =pacman -Syu=. snap-pac takes a snapshot of =/= just before the
    transaction and another just after (see [[/arch-workstation/maintain/snapshots][Snapshots]]).
 3. =admin apply=, so that anything a package update reset comes back.
 4. List any /new/ =.pacnew= files.
 5. Say whether a reboot is needed: when the running kernel's modules
    are gone from =/usr/lib/modules=, the kernel was upgraded.

=admin upgrade --yes= passes =--noconfirm= to pacman and =--yes= to
aconfmgr.

*** .pacnew files

When a package updates a configuration file you have changed, pacman
keeps yours and writes its new version alongside as =<file>.pacnew=.
That is how new options arrive on Arch -- the [[/arch-workstation/setup/install][Pi's cmdline.txt]] is one
-- and pacman never merges them for you. =admin upgrade= lists them:

#+begin_stdout
New .pacnew files (merge them, then 'admin save'):
  /etc/pacman.conf.pacnew
#+end_stdout

Compare the two, carry over what you want, and delete the =.pacnew=:

#+attr_shortcode: :style secondary :title Run this on the new machine:
#+begin_run
sudo vim -d /etc/pacman.conf /etc/pacman.conf.pacnew
sudo rm /etc/pacman.conf.pacnew
admin save
#+end_run

If the file is one the repo provides (under =~/arch/etc/=), merge into
the repo's copy instead and =admin apply=. A =.pacnew= left lying
around is drift too, so =admin diff= reports it until you deal with
it.

#+attr_shortcode: :style warning :title What this is not
#+begin_notice
This is not NixOS. The host repo reproduces your package /list/ and
your files, not the versions pacman installed on the day. Two machines
built from the same repo a month apart will differ in every package
that moved. A snapshot is a way back from a bad upgrade, but not an
atomic one. That is the trade the introduction described, made
smaller -- not made to go away.
#+end_notice

** Snapshots
:PROPERTIES:
:EXPORT_FILE_NAME: snapshots
:EXPORT_HUGO_SLUG: snapshots
:END:

=setup disk= made =@snapshots= for exactly this. =setup install=
configured [[https://wiki.archlinux.org/title/Snapper][snapper]] to keep snapshots of =/= (the =@= subvolume) there,
and installed [[https://github.com/wesbarnett/snap-pac][snap-pac]], whose pacman hooks take one snapshot before
every transaction and one after:

#+attr_shortcode: :style secondary :title Run this on the new machine:
#+begin_run
sudo snapper list
#+end_run

#+begin_stdout
# | Type   | Pre # | Date                     | User | Cleanup | Description               | Userdata
--+--------+-------+--------------------------+------+---------+---------------------------+---------
0 | single |       |                          | root |         | current                   |
1 | pre    |       | Mon Oct 26 05:22:11 2026 | root | number  | pacman -S --noconfirm vim |
2 | post   |     1 | Mon Oct 26 05:22:14 2026 | root | number  | vim                       |
#+end_stdout

The configuration is in the host repo, at =etc/snapper/configs/root=:

 - *No timeline.* Snapshots are taken when something changes, by
   pacman, not every hour. =admin save= and =admin apply= that do not
   touch packages take none.
 - *The newest ten*, by =NUMBER_LIMIT=, pruned by
   =snapper-cleanup.timer= once they are an hour old. Pre and post
   pairs whose contents are identical are pruned too.
 - *Only =/=.* =@home=, =@log= and =@pkg= are separate subvolumes so
   that rolling the system back leaves your data, your logs and the
   package cache alone.

A snapshot is a read-only btrfs subvolume under =/.snapshots/N/snapshot=,
so it costs only the space of what changed since.

*** Rolling back

#+attr_shortcode: :style warning :title Untested
#+begin_notice
Undoing a snapshot has not been tried on a machine built by this book
yet.
#+end_notice

To see what a transaction changed, compare its pre and post snapshot:

#+attr_shortcode: :style secondary :title Run this on the new machine:
#+begin_run
sudo snapper status 1..2
#+end_run

To undo it, on the running system:

#+attr_shortcode: :style secondary :title Run this on the new machine:
#+begin_run
sudo snapper undochange 1..2
#+end_run

That copies back every file in =/= that changed between the two
snapshots -- including pacman's database, which lives in =@=, so
pacman agrees afterwards about which versions are installed. Then
=admin diff=, which should show no drift.

#+attr_shortcode: :style warning :title The kernel is not in the snapshot
#+begin_notice
=/boot= is the FAT ESP (or the Pi's firmware partition), not a btrfs
subvolume, so no snapshot covers it. If the transaction you undo
upgraded the kernel, the old modules come back but =/boot= still has
the new kernel, and the next boot will not find its modules. Before
rebooting, reinstall the kernel package -- now the older version, from
the package cache -- so that its hooks rewrite =/boot= to match:
=sudo pacman -S linux= (=linux-rpi-16k= on the Pi).
#+end_notice

When the system no longer boots at all, boot the stick, then =setup
host --from= and =setup disk --mount= as in [[/arch-workstation/setup/disk][Prepare the disk]], and
=arch-chroot /mnt snapper --no-dbus undochange 1..2= from there.

*** Booting a snapshot

=setup= does not write boot entries for snapshots, because a menu that
grows an entry every time pacman runs is worse than no menu. But
systemd-boot will boot one if you write the entry, and it is the
quickest way to answer "was the machine still good at snapshot 1?"
before you undo anything.

An entry is the ordinary one with a different =subvol=. The ESP is
mounted =fmask=0077=, so it takes =sudo= even to read:

#+attr_shortcode: :file /boot/loader/entries/snapshot-1.conf
#+begin_edit
title   Arch Linux snapshot 1
linux   /vmlinuz-linux
initrd  /initramfs-linux.img
options root=UUID=<the same UUID as arch.conf> rootflags=subvol=@snapshots/1/snapshot ro
#+end_edit

=@snapshots/1/snapshot= is where snapper keeps snapshot 1, as seen from
the /top/ of the btrfs filesystem -- the same place =@= is seen from,
which is why =arch.conf= says =subvol=@=. Then boot it exactly once,
rather than making it the default:

#+attr_shortcode: :style secondary :title Run this on the new machine:
#+begin_run
sudo bootctl set-oneshot snapshot-1.conf
sudo systemctl reboot
#+end_run

What you get is a system you can log into, with =/= the snapshot:
=findmnt -no SOURCE /= reads =/dev/vda2[/@snapshots/1/snapshot]=, and
=snapper list= marks the booted snapshot with a =-=. Reading works --
=pacman -Q= answers from the snapshot's database, which is the whole
point of looking.

#+attr_shortcode: :style warning :title It boots read-only, whatever the mount says
#+begin_notice
A snapper snapshot is a read-only subvolume (=btrfs property get -ts
.../snapshot= says =ro=true=), and that, not the =ro= on the kernel
command line, is what stops writes. =findmnt= cheerfully reports =rw=
and =touch /etc/anything= still fails. In the test VM six units failed
for that reason, all of them pacman's gnupg sockets
(=gpg-agent@etc-pacman.d-gnupg.socket= and friends), which want to
create sockets under =/etc/pacman.d/gnupg=.

=@home=, =@log=, =@pkg= and =@nix= are separate subvolumes that no
snapshot covers, so they are still writable -- your home directory in
a snapshot boot is today's, not the snapshot's.

So this is for /looking/, not repairing: you cannot =snapper
undochange= into a read-only root. Do the repair from the stick, as
above. And the kernel and initramfs come from the ESP, which no
snapshot covers, so a snapshot from before a kernel upgrade boots
today's kernel -- the module mismatch described above applies here
too.
#+end_notice

Because it was a one-shot, the next boot is the normal system again,
with nothing to undo and no failed units. The entry file stays until
you delete it; =admin diff= will not mention it, since =/boot= is not
in the host repo.

** Desktop
:PROPERTIES:
:EXPORT_FILE_NAME: _index
:EXPORT_HUGO_SLUG: _index
:EXPORT_HUGO_WEIGHT: 600
:END:

#+attr_shortcode: :style warning :title Partly tested
#+begin_notice
BOOMSTICK's =DESKTOP=1 just test-vm= does this chapter on a test VM
(x86_64, under emulation): the [[/arch-workstation/desktop/system][system half]], a reboot into greetd,
then the [[/arch-workstation/desktop/sway-home][sway-home]] half as =user= -- =hm-install=, the GPU driver
setup, firefox from Nix -- and an =admin diff= that finds no drift.
What it cannot do is log in to sway: the VM has no screen, so
whether sway, its bar and firefox actually /draw/, with the GPU, is
untested.
#+end_notice

The base system is headless on purpose. A desktop is something you
add to it, and on this machine adding things means editing the host
repo and running =admin apply=. This chapter adds [[https://swaywm.org/][sway]], a tiling
Wayland compositor, with my own dotfiles, [[https://github.com/EnigmaCurry/sway-home][sway-home]], for the
=user= account.

The desktop comes from two places, split along one line: *what the
system has to provide comes from pacman, and what the user chooses
comes from Nix.*

| From pacman, via the host repo                                        | From Nix, via Home Manager and sway-home                  |
|-----------------------------------------------------------------------+-----------------------------------------------------------|
| sway, swaylock, swayidle, kanshi, the Wayland portal                   | foot, waybar, rofi, screenshot and clipboard tools, fonts |
| PipeWire and WirePlumber, pamixer, playerctl, brightnessctl           | firefox, with its add-ons and settings                    |
| greetd and tuigreet, the login screen                                 | emacs, and the command-line toolbox                       |
| polkit, Nix itself                                                     | every dotfile: sway, waybar, foot, bash, git ...          |

The left column is the part that is tangled up with the system: sway
needs logind and the system's Mesa drivers, swaylock authenticates
through the system's PAM, greetd is a system service, and Nix's own
daemon runs as root. Those come from Arch, managed by =admin= like
everything else on the machine. The right column is the part that is
personal -- which terminal, which bar, which keys -- and it comes from
[[https://github.com/nix-community/home-manager][Home Manager]], which builds a user's whole environment from one git
repository and can roll it back. That is the same arrangement the
[[/nixos-workstation][NixOS Workstation]] book uses, minus NixOS.

=admin= and =user= are still separate. The desktop belongs to =user=,
the day-to-day account; =admin= changes the system it runs on.

** The system
:PROPERTIES:
:EXPORT_FILE_NAME: system
:EXPORT_HUGO_SLUG: system
:END:

Everything on this page is an edit to the host repo, made as =admin=,
followed by =admin apply=. The same files are in BOOMSTICK's
[[https://github.com/EnigmaCurry/boomstick/tree/setup/desktop][desktop/]] directory, which the test VM uses.

*** Packages

Add a block to =packages.txt=:

#+attr_shortcode: :file ~/arch/packages.txt
#+begin_edit
# Desktop: sway and what it needs from the system. The rest of the
# desktop -- terminal, bar, launcher, firefox, fonts, dotfiles -- comes
# from Nix, with Home Manager and sway-home.
nix
sway swaylock swayidle kanshi xdg-desktop-portal-wlr
pipewire pipewire-pulse pipewire-jack wireplumber pamixer playerctl brightnessctl
greetd greetd-tuigreet polkit
noto-fonts just
#+end_edit

 - *sway*, *swaylock* and *swayidle* are the compositor, the screen
   locker and the idle watcher that starts it. *kanshi* switches
   display layouts when monitors come and go.
 - *xdg-desktop-portal-wlr* lets sandboxed programs and browsers share
   the screen.
 - *PipeWire* is the sound server, with *pipewire-pulse* standing in
   for PulseAudio so that =pactl= and =pamixer= -- which sway-home's
   volume keys call -- work, and *pipewire-jack* standing in for JACK.
   *WirePlumber* decides which device is which. *playerctl* and *brightnessctl* are the media and brightness
   keys.
 - *greetd* with *tuigreet* is the login screen: a text prompt on the
   first console that starts sway once you have logged in.
 - *polkit* lets programs ask for privileges without being run as
   root.
 - *noto-fonts* is the font the system's own programs draw with --
   sway's title bars, swaylock -- named because something among them
   asks for /a/ font (see below). *just* runs sway-home's install
   recipe.
#+attr_shortcode: :style info :title Name the providers
#+begin_notice
=pipewire-jack= and =noto-fonts= are there because something else
needs /a/ JACK and /a/ font, and more than one package provides each.
Run by hand, =admin apply= lets pacman ask you which; =admin apply
--yes= cannot answer that question and loops on it. Naming the one
you want in =packages.txt= means nobody has to be asked -- and it is
what aconfmgr's documentation recommends anyway.
#+end_notice

 - *nix* is the package manager Home Manager needs. Arch packages it,
   and so does Arch Linux ARM, so there is no installer script to
   download and nothing outside pacman's view.

*** Units

Add two lines to =units.txt=:

#+attr_shortcode: :file ~/arch/units.txt
#+begin_edit
nix-daemon.socket
greetd
#+end_edit

=nix-daemon.socket= starts the Nix daemon the first time someone uses
=nix=. Arch's package leaves the socket open to every user, so =user=
needs no group membership to use it.

=greetd= replaces the plain text login on the first console:
=greetd.service= declares =Conflicts=getty@tty1.service=, so enabling
it is all it takes. It also becomes =display-manager.service=.

*** Files

Nix needs flakes turned on, which Home Manager uses. The file replaces
the one the package installs, so it keeps that one's single setting:

#+attr_shortcode: :file ~/arch/etc/nix/nix.conf
#+begin_edit
build-users-group = nixbld
experimental-features = nix-command flakes
#+end_edit

greetd needs to be told to start tuigreet, and tuigreet to start sway:

#+attr_shortcode: :file ~/arch/etc/greetd/config.toml
#+begin_edit
[terminal]
vt = 1

[default_session]
command = "tuigreet --time --remember --asterisks --cmd sway"
user = "greeter"
#+end_edit

=--remember= fills in the last user who logged in.

*** Apply

#+attr_shortcode: :style secondary :title Run this on the new machine:
#+begin_run
git -C ~/arch add -A
git -C ~/arch commit -m "Desktop: sway, greetd, Nix"
admin apply
sudo systemctl reboot
#+end_run

=admin apply= installs the packages, puts the two files in place and
enables the units, after showing you each change. It goes round
twice: =nix-daemon.socket= and =greetd= do not exist until their
packages are installed, so the first pass installs them and a second
enables them, announced as =Enabling units from newly installed
packages=. snap-pac snapshots
the transaction like any other. The reboot is what starts greetd and
the Nix daemon socket. Afterwards the console shows tuigreet instead
of a login prompt; SSH as =admin= is unchanged.

Run =admin diff= once more. It should find no drift: the Nix store is
on its own subvolume, =@nix=, mounted at =/nix=, which =setup disk=
made for this and =90-ignore.sh= ignores. That also keeps the store --
which can grow to many gigabytes -- out of the snapshots of =/=.

** Nix and sway-home
:PROPERTIES:
:EXPORT_FILE_NAME: sway-home
:EXPORT_HUGO_SLUG: sway-home
:END:

#+attr_shortcode: :style warning :title Untested
#+begin_notice
Nothing on this page has been run on a machine built by this book
yet.
#+end_notice

The rest of the desktop is =user='s, installed by =user=. =user= has
no SSH key and no =sudo=, so get a shell as =user= from your =admin=
session -- a full login, with =user='s own systemd user manager and
session bus:

#+attr_shortcode: :style secondary :title Run this on the new machine:
#+begin_run
sudo machinectl shell user@
#+end_run

Not =sudo -iu user=: that gives a shell without a session bus, and
Home Manager's step that writes GNOME settings (dark mode, here) then
starts a D-Bus daemon of its own from Nix, which looks for its
configuration in =/etc/dbus-1/= -- where NixOS keeps it and Arch does
not -- and fails. Logged in at tuigreet, =user= has a bus already.

Then clone sway-home and let Home Manager install it:

#+attr_shortcode: :style info :title On a branch, for now
#+begin_notice
sway-home's support for non-NixOS hosts -- GPU drivers, nm-applet
only where NetworkManager runs, a working =hm-install= -- is on its
=arch= branch until it is merged. Until then, clone with =--branch
arch=.
#+end_notice

#+attr_shortcode: :style secondary :title Run this on the new machine, as user:
#+begin_run
git clone https://github.com/EnigmaCurry/sway-home ~/git/vendor/enigmacurry/sway-home
cd ~/git/vendor/enigmacurry/sway-home
just hm-install
#+end_run

=hm-install= asks for the name and email address to put in git's
configuration, then builds the Home Manager configuration in
=home-manager/= and switches to it: the packages land in the Nix
store, and =~/.config=, =~/bin=, =~/.bashrc= and the rest become links
into it. Dotfiles already in the way are renamed to =*.backup=. The
first run downloads a great deal; later ones only what changed.

From then on, as =user=:

| Command          | What it does                                           |
|------------------+--------------------------------------------------------|
| =hm-switch=      | Apply changes after editing sway-home                  |
| =hm-pull=        | Pull the latest sway-home                              |
| =hm-update=      | Move nixpkgs and Home Manager forward (then =hm-switch=) |
| =hm-generations= | List previous versions of the environment              |
| =hm-rollback=    | Go back to the previous one                            |

Programs from Nix are updated the Nix way, not by pacman: =admin
upgrade= moves sway, greetd and the rest of the system forward, while
firefox, foot, emacs and everything else in sway-home move when its
=flake.lock= does -- =hm-update= then =hm-switch=, or =hm-pull= to
take the lock sway-home's repository has. Each switch is a new
generation, so =hm-rollback= undoes one.

sway-home's own [[https://github.com/EnigmaCurry/sway-home/blob/master/HOME_MANAGER.md][HOME_MANAGER.md]] describes the rest. This is the
user's half of the "two halves" in the [[/arch-workstation/desktop][chapter introduction]]: =admin=
keeps the system in step with =~admin/arch=, and Home Manager keeps
=user='s environment in step with sway-home, each with its own
history and its own way back.

*** GPU drivers for programs from Nix

Programs from Nix are linked against Nix's own copy of Mesa, which
cannot load the drivers Arch installed: without help, firefox and
anything else that draws with OpenGL or Vulkan falls back to the CPU.
Home Manager's answer for non-NixOS systems is
=targets.genericLinux=, which sway-home turns on outside NixOS: it
builds the GPU drivers from Nix, to match, and asks for one command
to be run as root to link them into place as =/run/opengl-driver=.
=user= has no =sudo=, so =admin= runs it, from =user='s profile:

#+attr_shortcode: :style secondary :title Run this on the new machine, as admin:
#+begin_run
sudo /home/user/.nix-profile/bin/non-nixos-gpu-setup
#+end_run

It installs a link in =/etc/tmpfiles.d=, so that the drivers are linked
again at every boot. Run it once more whenever =hm-switch= says the
drivers changed. The link points into the Nix store and moves with
every update, so =setup= seeds =90-ignore.sh= with a line that has
aconfmgr leave it alone. (A host repo seeded before that needs the
line added: =IgnorePath '/etc/tmpfiles.d/non-nixos-gpu.conf'=.)

*** Log in

Log out of the =user= shell, and at the machine itself, log in as
=user= at tuigreet. It starts sway, with sway-home's configuration.

*** Networking

This machine does not run NetworkManager -- it uses systemd-networkd
and iwd, as the [[/arch-workstation/setup/install][install]] set up -- so sway-home leaves out =nm-applet=,
the NetworkManager tray icon: it installs it only where
=NetworkManager.service= exists. For WiFi, =iwctl= does the same job
from a terminal. If you would rather have NetworkManager, the [[/arch-workstation/setup/host][host
page]] shows how to switch the host repo over to it; run =hm-switch=
afterwards and the applet comes back.
